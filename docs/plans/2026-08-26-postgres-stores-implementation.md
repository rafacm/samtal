# Move both stores from SQLite to Postgres: implementation

The companion to [`2026-08-26-postgres-stores.md`](2026-08-26-postgres-stores.md),
one section per milestone, appended in the change that ticks the
milestone. It records deviations from the plan, resolutions of anything
the plan left open, and discoveries; a milestone with no deviations says
so explicitly.

## M1: cut both stores over to Postgres, operator story included

PR #307.

### What landed

In the order the commits tell it: the instance first, then the driver,
then the storage layer, then the callers, then the lane, then the
documents.

- `docker-compose.yml` at the repository root and
  `deploy/postgres-init.sql` beside it. One `postgres:17-alpine`
  service, bound to loopback with an overridable host port, a named
  volume and a `pg_isready` healthcheck naming the configured database.
  The init file creates the two schemas `WITH AUTHORIZATION` to the
  server role and provisions `vinga_ro`; it is create-or-rotate and
  every grant is written to be run again, because the documented reset
  is a `dropdb`/`createdb` and that takes the schemas and the
  database-local default privileges with it while the instance-level
  role survives.
- `psycopg` into the `serve` extra as the plain source distribution and
  `psycopg[binary]` into the dev group and the Dockerfile, which is
  decision 10 as the review round amended it: an install of `serve`
  does not drag a bundled libpq in behind it.
- `db/__init__.py` rewritten around a connection and a `StoreChain`.
  `open_at(settings, chain)` builds the engine, creates the schema when
  it is missing and runs that chain to head; the write engine's begin
  listener takes `pg_advisory_xact_lock`; `lock_timeout` rides on the
  connection's startup options; `read_engine` is repeatable-read and
  read-only; and one classifier over a closed set of psycopg errors
  replaces the two string sniffs. `Superseded`, `_stranded`,
  `database_path`, `existing_engine` and the filename constants delete.
- Both `schema.py` files carry their schema on the metadata, both
  `env.py` files configure `version_table_schema` and `include_schemas`
  with a name filter, `autogen.py` opens a scratch database and takes
  the chain, and both chains re-baseline (`3001_postgres_domain`,
  `1001_postgres_conversations`), autogenerated and then reviewed.
- The call-site sweep: boot, `app.py`, both API modules, `config/store.py`,
  `device/bindings.py`, and the events catalog, where
  `BindingsSnapshotOnly` retires and `ConversationsEnabled` loses its
  path.
- `tests/conftest.py` reshaped: one migrated database per worker cloned
  from a per-run template, `TRUNCATE ... RESTART IDENTITY CASCADE`
  between tests over the tables the two metadata objects enumerate, a
  per-run prefix inherited by the workers through the environment, the
  production variables cleared and overridden, a guard before every
  destructive statement, and two opt-in fixtures (`blank_database` from
  `template0`, `spare_database` cloned from the template).
- The suites translated under the plan's pin rule, the CI workflow's
  three jobs, the Dockerfile and entrypoint, both example configs, the
  generated references, the ADR addendum, the changelog and the
  operator documentation.

### Deviations from the plan

Five, each with its reason.

1. **`upgrade_to_head` asks whether the schema exists before it creates
   it, rather than issuing `CREATE SCHEMA IF NOT EXISTS`
   unconditionally.** The plan says the second. Verified against
   Postgres 17 while writing the init file: `CREATE SCHEMA` checks
   `CREATE` on the database *before* it looks at whether the schema is
   there, so the `IF NOT EXISTS` form still refuses for a role that
   lacks that privilege, including when the answer would have been
   "nothing to do". A deployment that provisions its schemas with
   `deploy/postgres-init.sql` and gives the server role nothing but its
   own schemas would therefore have been refused at every boot. Asking
   first is what makes decision 1's stated privilege ("`CREATE` on the
   database") a requirement of the unprovisioned case only, which is
   what the deployment documentation now says.

2. **The `DROP DATABASE` guard checks the name against the run's
   prefix rather than `current_database()`.** The plan's resolution to
   finding 2 says every destructive statement verifies
   `current_database()` equals the generated test name. That is exactly
   right for `TRUNCATE` and impossible for `DROP DATABASE`, which runs
   from a connection outside the database it drops. Both guards are
   implemented and both refuse; the difference is written down in the
   helpers themselves.

3. **`create_app` gained a `from_store` argument, which the plan does
   not mention.** Decision 6 deletes `DeviceBindings.open`'s
   missing-file arm, and with it went the only thing deciding whether a
   store described this server's world: with the probe gone, every
   server composed from a `Config` handed to it read an empty database
   and answered "this device is bound to nothing". Which mode a server
   is in is a fact about how it was composed, so the composition states
   it: both production entry points pass `from_store=True`, and an
   embedded caller gets the snapshot served authoritatively, which is
   what `snapshot_authoritative` always meant. This is the plan's own
   reasoning ("a decision made where the composition is rather than a
   probe made here") carried one step further than the plan wrote it.

4. **The commit order puts the config schema before the `db/`
   rewrite.** The plan's suggested sequence has `db/` third and the
   config schema fourth. `db/` takes `DatabaseConfig` as its parameter
   type, so the reverse order produces a commit that cannot import.
   The lock-timeout proof is still the first commit of the `db/`
   stretch, and the premise was verified as a script before any code
   was written (see below).

5. **The conversations baseline is the one file the line limit is
   waived for.** It reproduces every column comment from
   `conversations/schema.py` verbatim, so that `\d+` shows an analyst
   what the reference says. Reflowing them would make the migration and
   the metadata two copies of one paragraph that could come to differ,
   which is what a baseline reproduced from autogenerate exists not to
   be.

### The named risk, proved

The plan's first risk is that `lock_timeout` must abort a wait for a
*transaction-scoped advisory* lock, because the whole 409 story rests on
it. It holds. Two connections against the compose instance: one takes
`pg_advisory_xact_lock` and keeps it, the other sets `lock_timeout` to
300ms and asks for the same key. It gives up after 0.306 seconds with
`psycopg.errors.LockNotAvailable`, SQLSTATE 55P03, while the holder is
still holding. The fallback the plan named
(`pg_try_advisory_xact_lock` in a bounded wait loop) is not needed.

That proof ships as `tests/unit/test_db_locking.py`, which pins it at
the driver, through SQLAlchemy's wrapper (where the classifier has to
walk `orig` to find it), for each member of the closed set by name, for
a driver error outside the set, and for the shipped ten seconds on a
fresh connection, which the shortened-constant tests cannot show.

Two more premises were verified against Postgres 17 rather than
assumed, as the plan's risk list asks:

- **`\getenv`.** The init file was run twice against the pinned major:
  once through compose's initdb path with the defaults, once by hand
  with `VINGA_DB_USER=srv` and a rotated `VINGA_DB_RO_PASSWORD`. Both
  schemas came out owned by the named role, the default-privileges row
  named it, the existing `vinga_ro` took the new password, and the
  `CREATE ROLE` correctly produced no statement on the rerun.
- **`TEMPLATE`.** The per-worker clone runs on every local invocation
  of the lane, serial and under xdist.

### Pins translated, and pins retired

The rule the plan states: a pin on a *promise* translates to the
Postgres mechanism; a pin on the *mechanism* retires with it.

Translated:

- The busy family (`test_config_refusals`, the API 409s, the CLI's
  contended write, the integration lane's contended write over a real
  socket). A second connection holding the chain's advisory lock with
  the constant monkeypatched down replaces a second `sqlite3`
  connection in `BEGIN IMMEDIATE`. The four copies of that helper
  collapse into `tests/support/stores.py`.
- The never-reused-id property: `AUTOINCREMENT` in stored DDL becomes
  an identity column read from `information_schema`, and the
  delete-then-insert behaviour is unchanged.
- The text-off proof
  (`test_conversations_session`, `test_conversations_store`): reading
  the database file's bytes becomes reading every column of every row
  of every table the store owns. The weakening is stated in the tests'
  own docstrings: it cannot see a page the server has not reclaimed,
  which is autovacuum's business and not a client's.
- The deletion promise: the deferred-truncating-checkpoint case becomes
  a held repeatable-read snapshot across a retention pass, pinning both
  halves of what MVCC gives (the old snapshot still sees the row, the
  next transaction does not).
- The migration-race case (`test_db_open`), which now runs against a
  blank database and parks the second opener on the advisory lock.

Retired, one by one:

- `test_a_reader_defers_the_stores_truncation_and_the_next_marker_takes_it`
  and `test_the_checkpoint_runs_outside_a_transaction`: there is no
  write-ahead log to truncate and no checkpoint to run.
- `test_the_connection_is_configured_for_concurrent_use` (journal_mode,
  busy_timeout) and its conversations twin (which also asserted
  `secure_delete`): replaced by the `SHOW lock_timeout` pin.
- `test_the_cursor_tables_are_declared_autoincrement`: replaced by the
  identity-column pin.
- `test_an_uncreatable_directory_names_the_configuration_key` and
  `test_an_unwritable_directory_names_the_configuration_key`: there is
  no directory.
- The whole stranded-database family
  (`test_a_database_from_the_squashed_chain_says_to_reset`,
  `test_the_domain_database_answers_only_for_its_own_deleted_revisions`,
  `test_a_database_from_a_newer_build_is_not_told_to_delete_itself`,
  `test_the_conversations_database_is_never_told_the_domain_sentence`,
  `test_an_alembic_failure_that_is_not_a_stranded_database_is_not_told_to_reset`):
  no Postgres database can be stamped at a SQLite-era revision, so the
  arm they pinned is deleted rather than ported.
- `test_the_read_engine_refuses_to_create_a_missing_store` (the
  `mode=rw` URI): replaced by a proof that the read connection refuses
  a write, which is the server's own rule rather than a mode flag.
- `test_a_deployment_that_never_recorded_answers_404_naming_the_key`:
  retired as a contract change, and replaced by a test asserting the
  ordinary empty shapes with the reasoning in its docstring.
- `test_a_reader_sees_committed_rows_while_the_wal_is_uncheckpointed`:
  the promise survives as
  `test_a_reader_sees_committed_rows_while_the_writer_is_still_going`;
  the WAL half of it does not.

Gained, because the move made them possible or necessary:

- The conversations chain's metadata-drift check, which it never had:
  its SQLite-era suite asserted three tables' stored DDL, which said
  nothing about a column added to the metadata without a migration.
- The URL allowlist's refusals, including a credential planted in a
  query parameter, which is why the refusal is fixed rather than
  password-hidden.
- The environment contract: the generic spelling refused, the four
  short names overriding the file, and a port that is not a port
  refused without its value.
- The cutover proof: a committed pre-cutover export applied into a
  truly empty database.
- The `vinga_ro` contract asserted against the executed init file.

`test_logs`'s two in-memory `sqlite://` engines stay, with a comment
saying why: what they test is the log floor over SQLAlchemy's own echo,
not this server's stores, and a neutral engine that needs no instance,
no migration and no schema is the right tool for it.

### The recovery fixture, and how it was produced

`tests/integration/data/pre-cutover-export.yaml` is a real export
printed by the pre-cutover build's own `config export`, against a
SQLite store seeded with this lane's `DEPLOYMENT` document plus one
stored credential. It was produced from a detached worktree of
`79a8b3d1` (the branch's last commit before any code landed), by
seeding a scratch SQLite database through that build's `ConfigStore`,
building its configuration API over the same directory, reading
`GET /config` and rendering it through that build's own `_exported`.
The worktree was removed afterwards. Nothing in this repository can
produce the file again, which is why it is committed: after this
milestone there is no build that writes a SQLite database to export
from.

Two integration cases use it. The cutover case applies it into a
`template0` database, re-enters the credential through the command the
export annotated, boots again, reads the plaintext back and compares a
fresh export against the fixture with the `set-secret` annotations
taken off (an export names where a credential goes and never its
value, so those lines cannot match by construction). The reset case is
the pre-existing recovery test with "delete the file" replaced by
`reset_database`, which drops and recreates from `template0`: the same
two commands the recovery documentation names.

### Measurements

Recorded here because the plan makes the unit lane's runtime an
acceptance criterion: the after may not double the before.

| Lane | Before | After | Ratio |
| --- | --- | --- | --- |
| unit, `-n auto --dist loadfile` | 56.4s | 58.1s | 1.03 |
| unit, serial | 4m58s | 6m35s | 1.33 |
| integration | 4m00s (190) | 4m18s (196) | 1.07 |

**The budget holds.** The acceptance criterion is the parallel lane,
because that is the one CI runs, and it is 1.03: three per cent, which
is inside the noise of two runs on one machine. Serial is 1.33, well
under the doubling the plan forbids, and the shape of the difference is
what the design predicted: a `TRUNCATE` per test costs milliseconds and
there are four thousand of them, which shows up as about a hundred
seconds spread evenly and disappears almost entirely when four workers
run in parallel because each is truncating its own database.

Measured on the same fourteen-core development machine, one lane at a
time, with the before numbers taken from a detached worktree of
`79a8b3d1` (the branch's last commit before any code landed) so that
both sides are the same suite on the same hardware. The plan's own
before number for the parallel lane is ~2m25s in CI, where four cores
rather than fourteen are the constraint; nothing here predicts the CI
after number, which the first workflow run will produce.

### What the first CI run found, and what no local run could

Both lanes were recorded green locally, serial and under xdist, and
both failed on the first workflow run: the unit lane red on thirty
tests, the integration lane hung for seventy-three minutes and killed.
With those fixed the image job failed too, at a third place. None of
the three is about Postgres being the wrong choice, and none is random.
What they share is that a lane's conditions had stopped being the
lane's own: one because CI exports a variable a developer's shell does
not, one because a boot that used to refuse for want of a place to put
a file now has one, one because a lane that stores nothing was made to
provision a store anyway. The same lesson from three sides, which is
that a suite has to state what it runs on rather than inherit it.

**The unit lane: four workers in one database.** Decision 8 says the
suite's connection settings are its own, and the conftest's own comment
said the `VINGA_DB_*` family is overridden for the test process. It was
not: the fixture moved `DatabaseConfig`'s model default onto the
per-worker database and left the environment alone. The loader reads
`VINGA_DB_NAME` *over* the model default
(`config/loader.py`'s `_with_database_environment`), so every settings
composition made the way a deployment makes one, which is most of the
CLI suites, opened the job's shared `vinga` database, while the autouse
`TRUNCATE` cleared a per-worker database nothing was writing to. Four
workers wrote over each other; thirty tests failed on symptoms that
named a default agent or a provider they had never created. Two doors
reached one fact and the environment's answer won.

`_database_default` now sets both doors, which is what makes it the
fact's one home, and `packaged_database` takes the variable away for its
span so that "the shipped defaults" is true through the loader as well
as through a bare `DatabaseConfig()`. The family's split is written down
where it is read: four variables name the INSTANCE and an exported value
wins, which is how CI points the lane at its service container; the
fifth names a DATABASE this lane makes for itself, so an exported value
must lose. `tests/unit/test_lane_database.py` pins the agreement rather
than either half, because a test asserting only the door it happened to
use would have passed through the whole failure. Reproduced exactly
before the fix with `VINGA_DB_NAME=vinga uv run pytest
tests/unit/test_config_cli.py`: the same twenty-five failures, in the
same order, that CI's `gw3` reported.

**The integration lane: a boot that no longer refuses.** The lane hung
for seventy-three minutes and was killed with no test named. The last
line it printed was the test before
`test_the_serve_install_can_be_asked_to_serve`, which runs
`vinga-server` from a built environment and reads its exit code. Its
premise was that a server with no configuration cannot start, which was
true of a SQLite build with nowhere to put a file and is false now: the
shipped connection defaults name a real instance, both lanes have one
running, and an empty store migrates and serves. So the process bound a
port, and `subprocess.run` had been written with no `timeout=`. The
contributor door's test next to it had the same premise and would have
hung next.

Both now ask for a database on a port nothing listens on and assert the
boot's own fixed sentence, which is a stronger proof of the same claim:
a client install exits at the dispatch and cannot reach that sentence at
all. And the lane stops being able to hang. `tests/support/commands.py`
holds one runner with two budgets (a command of a built grammar, an
environment built with uv), and an expiry raises an `AssertionError`
carrying the command line and both streams: a red lane names the test,
a hung lane names nothing. Every `subprocess.run` in the integration
lane now has a deadline. The bound is a ceiling on a hang and not a
measurement; a run that approaches either budget is already a bug.

This is what caught the second one: with the first fix in place the
contributor door's server booted locally too, and the deadline turned
what would have been a second silent hang into a named failure inside
one run.

**The image lane: a conftest that provisioned on the way past.** With
the two above fixed, the unit and integration jobs went green and the
re-dispatched image run failed in the same place for both variants:
`uv run pytest tests/smoke` died at collection, importing
`tests/conftest.py`, on `_provision()` reaching `vinga-postgres:5432`.
The smoke container itself had booted and migrated perfectly well; the
pytest that checks it runs on the RUNNER, where that name resolves to
nothing, because the database lives on a Docker network and is not
mapped to the host. And it needs no database at all: the smoke lane
drives the container over HTTP and a websocket, and the server under
test owns its own store.

The root conftest provisioned at its own import, unconditionally, for
every lane under `tests/`. That is decision 8's machinery applied to a
lane it was never about. It is now a declaration: `provision_stores()`
is called from the conftest of each lane that opens a store (unit,
integration, local), at that conftest's import, which pytest runs before
it imports any test module in that directory, so nothing that needed the
old timing loses it. The per-test truncation follows the same
declaration, since a lane with no database has nothing to truncate; the
condition is the LANE and never the test, because a per-test "did this
one touch anything" would be the same fixture with a hole in it.
`tests/smoke/conftest.py` says in words that it deliberately does not
declare, so the absence reads as a decision.

Opt in rather than opt out, deliberately. A storing lane that forgets
meets "database does not exist" at its first open, named and local; a
non-storing lane that had to remember to opt out meets exactly the
collection failure this replaces. Two other things fall out: the
unreachable-instance refusal still fires, unchanged, for all three
storing lanes (verified with the instance stopped and with a host in
`.invalid`), and an xdist controller running a bare `pytest` no longer
creates a `_main` database no worker uses. The pin runs a real pytest
over `tests/smoke` with `VINGA_DB_HOST` pointed at a name that resolves
nowhere, because what broke was collection itself and a flag is what a
future conftest could satisfy while still connecting on the way past.

**And one plain staleness.** The committed spelling census records the
line each quoted invocation sits on, and three files moved under it
after it was last generated. Nothing to do with either failure above,
and red on any machine: the milestone's last local run predated its own
last documentation edits. Regenerated.

**After the repair**, on the same machine the measurements above were
taken on: `ruff` clean; the unit lane 4014 passed and 19 skipped, 6m55s
serial and 57.6s under `-n auto --dist loadfile`; the integration lane
196 passed in 4m19s. The parallel lane, which is the one the budget is
about, is unmoved. Serial gains twenty seconds, all of it the
smoke-collection pin, which starts a pytest of its own. The three tests
this adds are that pin and the two lane-database ones; the deadlines
cost nothing when nothing hangs, which is the point of a ceiling.

`tests/smoke` also collects and runs against no instance at all, which
is the whole of the third fix: verified both with the compose service
stopped and with `VINGA_DB_HOST=nowhere.invalid`, and verified in the
other direction by reinstating the import-time `_provision()` and
watching the pin come back with the runner's exact exit code and
sentence.

### Not verified locally

Stated plainly rather than claimed:

- **The image job.** It builds and smokes real containers and does not
  run on pull requests; the milestone's verification includes one
  manual `workflow_dispatch` run against the branch before merge.
- **`tests/smoke`.** It runs only inside the image job, against a
  container started there.
- **The wheel-migration step.** It builds a wheel, installs it into a
  throwaway virtualenv and migrates a database of its own, all inside
  the integration job.
