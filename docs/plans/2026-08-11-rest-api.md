# REST API for the domain configuration plan

## Goal

Implement issue #101: expose the domain configuration over a REST API
mounted on the existing server, and make the `samtal-server config`
CLI a thin client of it in the same issue, keeping a bounded local
recovery path. The repository (`config/store.py`) already holds every
semantic decision the API needs (fragment validation through the
pydantic models, strict reference checks inside one write
transaction, secrets write-only with masked reads, entity replacement
preserving stored secrets), so this step adds transport, not
semantics. An API handler that bypasses or duplicates repository
logic is the bug.

The issue's six decisions are settled and this plan does not
re-litigate them; it makes them concrete. The issue's open questions
are resolved below, each with its reason, along with the smaller
decisions the issue leaves to the plan. Configuration remains a
boot-time snapshot: a successful write answers with the same "applies
at the next server start" contract the CLI prints, and hot apply is a
later issue.

The companion implementation doc,
[`2026-08-11-rest-api-implementation.md`](2026-08-11-rest-api-implementation.md),
records what each milestone actually did, with deviations from this
plan, resolutions of its open questions, and discoveries; a milestone
with no deviations says so explicitly.

## The six decisions, restated for reference

From issue #101, fixed, one line each:

1. The API mounts the existing repository; handlers restate nothing.
   The repository's existing unit tests keep guarding API behavior
   unchanged.
2. The CLI becomes a thin client of the API in the same issue, with a
   bounded local recovery subset (`show`, `delete`, `clear-secret`,
   `set-secret`) behind an explicit `--local` flag, documented as the
   break-glass path; its scenario tests convert into the API
   acceptance suite.
3. Code-first OpenAPI: FastAPI generates the document from the routes
   and the pydantic models, the `Field(description=...)` pass flows
   into it verbatim, and the document is committed under the same
   regenerate-and-diff CI check as `docs/reference/domain-config.md`.
   Provider option bodies stay honest-but-loose until #88, and the
   document says so.
4. The API mounts under `/api/` on the main port behind a mandatory
   bearer token (`SAMTAL_API_SECRET`), fail-at-boot when unset, the
   `auth.enabled` precedent. Secrets stay write-only with masked
   reads; network exposure is the deployment layer's job; `set-secret`
   plaintext crossing the connection makes loopback-or-TLS a stated
   requirement.
5. Configuration stays a boot-time snapshot; the API does not hot
   apply, and every successful write says when it takes effect.
6. Errors carry the repository's sanitized messages, mapped to
   structured HTTP codes (422 shape and reference refusals, 404
   missing entities, 409 the retryable lock timeout), message text
   unchanged from the CLI. The no-leak contract holds on every path.

## Resolved open questions

### The API is a sub-application, mounted on the one app

One FastAPI process, one port, two apps: `create_app` builds the
device-facing app exactly as today and mounts a second FastAPI
instance at `/api`. Not a router on the main app, for three reasons:

- **The OpenAPI document is scoped by construction.** Decision 3
  commits the generated document, and the document should describe
  the admin API and nothing else. The main app deliberately publishes
  no schema (`openapi_url=None`, a security posture this plan does
  not touch), and a router would force one app to be both "publishes
  nothing" and "generates the committed contract". A sub-application
  has its own metadata, its own routes and its own `openapi()`, so
  the committed document is exactly the admin surface with the device
  endpoints structurally absent from it.
- **The token gate is a property of the mount, not of each route.**
  The auth check is middleware wrapped around the sub-application
  (the Authentication section says why middleware rather than a
  dependency), so a route added in a later change cannot forget it;
  with a router, every route decorator is a place to get that
  wrong.
- **`local_only` stays a one-sentence argument in `app.py`.** The
  egress guarantee is about session data leaving the host through
  providers and MCP servers. The API is control plane: it accepts
  inbound requests and sends nothing anywhere, so it needs no egress
  declaration, and keeping it one mounted object with one gate keeps
  that reasoning local instead of smeared across the main app's
  routes.

The sub-application serves no interactive docs and no live schema
endpoint (`docs_url=None`, `openapi_url=None`), matching the existing
posture: the committed document is the contract, and serving it live
is an additive change the moment the front-end wants it.

### The read shape: the entity, plus its stored-secret slots

A read cannot be the bare entity alone. The entity's model-shaped
half is what a PUT accepts back, and by design it can never carry
ciphertext, so a bare-entity response would lose the one fact a
masked read exists to convey: which slots hold a stored secret. The
CLI renders that fact as comment lines; JSON has no comments, so the
API needs it structural.

Every entity GET therefore returns an envelope:

```json
{
  "entity": { ... },
  "secrets": { "api_key": { "shadows": "api_key_env" } }
}
```

`entity` is the fragment-shaped masked body, exactly what a PUT for
this entity accepts (masking applies the same fail-closed `mask()`
rule the CLI display path uses). `secrets` maps each stored slot to
its shadow mark: `shadows` names the entity key the stored value
displaces (the precedence decision 4 keeps visible), null when the
entity writes no reference for that slot. Entity kinds that cannot
hold a stored secret (agents, agent-defaults, devices) return the
same envelope with `secrets` empty, so a client renders one shape.

List endpoints return a mapping keyed by identity, not an array with
an envelope: `GET /api/agents` is `{"<name>": <envelope>, ...}`, and
`GET /api/providers` is `{"llm": {"<name>": <envelope>}, ...}` over
the four stages. The names the front-end needs come with the
entities by construction, the shape is the shape the domain models
already have (and the one `config show` renders as YAML), and
OpenAPI describes it with `additionalProperties`. `GET /api/config`
returns the whole masked domain document paired with the stored
secret locations as a list, the JSON of what `config show` prints.

### `--local` relies on the lock, and says what it is doing

`--local` does not probe for a live server and does not refuse to run
beside one. Three reasons:

- There is no reliable liveness test for a SQLite file across
  processes: a pid file lies after a crash, and a lock probe is a
  race against the answer changing. A wrong "a server is running"
  refusal would wedge the recovery path in exactly the situation it
  exists for.
- The write path is already safe under concurrency: every repository
  write is one `BEGIN IMMEDIATE` transaction, two writers serialize,
  and a lock that does not arrive inside the busy timeout fails with
  the retryable error. That is the same behavior the CLI has today,
  tested with two concurrent writers.
- A concurrent `--local` write is not observed by a running server
  until restart, by design (boot-time snapshot), which is not a
  hazard but the documented contract.

What `--local` does do is say what it is: every `--local` invocation
prints a notice on stderr that this is the break-glass path, that it
bypasses the API, and that a running server will not observe a change
until its next start. The notice is the honest substitute for a
refusal that cannot be implemented reliably.

## Further decisions the issue leaves to the plan

### `server.api`: a `secret_env` key, no `enabled` flag

`ServerConfig` gains an `api` section with a single key,
`secret_env`, default `SAMTAL_API_SECRET`, mirroring
`auth.secret_env`: the token is referenced by the name of the
environment variable holding it, never held in the file. There is
deliberately no `enabled` flag: the issue's decision 4 defers an
`api.enabled` switch to a later deployment shape "with an actual
reader", so the API is always mounted and the secret is always
required. `create_app` resolves the token the way `build_device_auth`
resolves the device secret, and refuses the boot with the same shape
of error: what is missing, how to generate one
(`openssl rand -hex 32`), and where it goes. `config.example.yaml`
gains the commented block in the same change.

`secret_env` cannot be a bare non-blank string, because the boot
error quotes the variable name it says to set, and the mistake that
lands in this key is pasting the token where its variable name
belongs: the quote would print the token. The models get a shared
`EnvName` annotated type (the `_ENV_NAME_RE` rule the provider
`*_env` validator already enforces), used by `api.secret_env` and
adopted by `auth.secret_env` in the same change, with a refusal
that says what the key must hold and shows an example, never the
value, exactly the wording precedent of the provider validator.
Nothing that boots today stops booting: a pasted secret in either
key never resolved to a set variable, so those configurations were
already failing, only later and while quoting the paste. Sentinel
tests cover stderr, log records, and the exception chain for both
keys.

The operational consequence is stated out loud rather than
discovered: every deployment must set `SAMTAL_API_SECRET` before
upgrading past milestone 1, the CHANGELOG entry and the deployment
notes say so, and the boot error is the safety net for the one that
did not read them.

### The API opens the database per request

Handlers get a `ConfigStore` from a dependency that opens the
database, yields the store, and disposes the engine, exactly the
CLI's `_store` context manager. No engine lives on the app.

The alternative (one engine held for the app's life) was considered
and left out: `boot.py`'s contract is that nothing after boot reads
the database, and keeping that true for serving while the API holds
an engine would mean two lifetimes to reason about; a lazily created
engine would need lifespan disposal wiring; and, decisive for the
tests, an eagerly opened engine would make every `create_app(...)`
in the suites open a database again (the milestone 4 discovery from
#86, where the default directory refuses on a laptop). Per-request
open costs an Alembic up-to-dateness check per request, which is
acceptable for an admin surface whose readers are one operator and
one front-end; if a future reader makes it matter, the change is
local to the dependency, and the repository's serialized-open
behavior is already tested. Handlers are plain `def`, so FastAPI
runs them on the threadpool and the synchronous SQLAlchemy calls
never block the event loop.

### Error mapping needs typed refusals, not parsed messages

The repository raises one `ConfigError` for every refusal, which is
right for the CLI (everything is a sentence on stderr) and not enough
for the API (the status code is part of the contract). Mapping by
inspecting message text would make the wording load-bearing, so the
refusals get types instead, all subclassing `ConfigError` so the CLI
and the boot path do not change. The types live beside `ConfigError`
in `loader.py`, which imports no database machinery, so both raisers
can use them: the API opens the database per request, which means
`open_database()` is on every request path and its failures need the
same typing as the repository's, or a lock timeout during the
open-and-migrate step would come out 422 where the settled contract
says 409. `open_database()` and `ConfigStore._transaction()` both
map the lock timeout and the residual database failures to the same
two types:

- `UnknownEntityError`: every "no such provider / MCP server / agent
  / device" and "no secret is stored for this slot". Maps to 404.
- `DatabaseBusyError`: the lock that did not arrive inside the busy
  timeout ("nothing was changed; run the command again"). Maps to
  409, the retryable code decision 6 names.
- `StorageError`: a stored row that cannot be read as configuration
  (the JSON-column shape refusals) and the residual database
  failures. Maps to 500: the client's request was fine, the stored
  state is not.
- Everything else stays plain `ConfigError` (fragment shape,
  reference refusals, slot refusals, bad stage names): 422.

Exception handlers on the sub-application render all four as
`{"detail": "<message>"}` with the message text unchanged from the
CLI, so operators meet one vocabulary. An exception that is not a
`ConfigError` returns a generic sanitized 500 and is logged
server-side; no traceback reaches a response body.

### Request bodies are validated once, in the repository

PUT bodies are received as raw JSON objects and handed to the
repository, which validates them through the entity models exactly
as it validates a YAML fragment. The handlers do not declare the
entity models as body types, deliberately: FastAPI's request
validation echoes the rejected input back in its 422 response
(`"input": ...` per error), and a fragment with an inline secret
would land in the response body, which breaks the no-leak contract
the repository's `_load` exists to keep. One validation code path,
one sanitized message shape, no second dialect.

The OpenAPI document does not pay for this: each PUT route declares
the entity model's schema as its request body via `openapi_extra`,
so the committed document carries the full `Field(description=...)`
pass (decision 3) while the running code validates in exactly one
place. The sub-application also overrides the default
`RequestValidationError` handler with a sanitized one, so a body
that is not valid JSON, or not an object, is refused with a message
that describes the expectation and never quotes the payload; with
bodies received as raw objects, that handler is the only place
FastAPI's own validation can fire on a config route.

Three writes are argument-shaped rather than fragment-shaped, and
their handlers parse an exact shape: `PUT /api/devices/{mac}` takes
`{"agents": [...]}`, `PUT /api/default-agent` takes
`{"name": "..."}`, and the secret writes take `{"secret": "..."}`.
Each handler requires exactly the one key with a string (or
string-list) value and refuses a missing key, an extra key, a null,
a non-string, or a wrong container with a sanitized 422 that
describes the expected shape and never echoes the body, which for
the secret route is a leak surface like any other. That is
addressing, not semantics, the same line the CLI draws between
argparse and the repository.

One invariant moves down into the repository, because the CLI is
the only thing enforcing it today: `ConfigStore.set_secret`
currently trusts its annotation, so a non-string or empty value
reaching it would be encrypted into an envelope that fails
verification at the next boot. `set_secret` refuses a value that is
not a non-empty string, without echoing it; the CLI keeps its
friendlier stdin wording in front of the same rule, and the leak
tests run sentinel values through every malformed-body path.

### Identities must survive a URL path

The API addresses an entity by putting its identity in the path,
and the repository today accepts any non-blank string as a name and
any secret-shaped token as a slot, including ones containing `/`,
which a decoded path cannot carry through routing. Rather than an
addressing scheme that can represent any string (query-parameter
identity, or a bespoke encoding every client must implement), the
repository's write path gains an addressability rule, which is a
semantics-layer change made once and inherited by the CLI and the
API alike, not a handler restatement:

- A provider, MCP server or agent name must be expressible as one
  URL path segment: no `/` and no control characters. Spaces,
  percent signs and Unicode remain legal; they percent-encode and
  decode losslessly. MCP names are already tighter than this
  (`[A-Za-z0-9_-]+`), MACs are normalized, so the rule bites only
  provider and agent names.
- A provider secret slot must be a single such segment too; an MCP
  slot's key half must be an environment-variable name for `env.`
  (the only kind a `$VAR` could ever reference) and an HTTP header
  token for `headers.` (the only kind a request could ever carry),
  neither of which admits `/`.

The rule runs where `_identifier` and `_check_slot` already run, so
it applies to new writes only: the load path is untouched, a
pre-existing row with an unaddressable name still boots, still
appears in `GET /api/config` and `config show`, and is still
deletable through the `--local` recovery subset, whose delete goes
by membership rather than by the write-time rule. The refusal
message names the rule and the offending kind of character, never
suggesting the name was otherwise wrong. Path parameters on the
API side are matched as decoded single segments, and the
acceptance tests round-trip names and slots containing spaces,
percent signs, Unicode, and dotted MCP slots, plus the write-time
refusal for a slash.

### One masked view, two renderings, and repository-owned reads

Existence is semantics, so it moves into the repository first: the
CLI today decides "no such provider" for `show` in its own helper
(`_provider_entry`), which is exactly the kind of decision decision
1 says a second caller must not re-implement. `ConfigStore` gains
read methods beside `load()`: one per addressable entity kind
(provider, MCP server, agent, agent-defaults, device,
default-agent, plus the whole snapshot), each returning the entity
together with its stored-secret slots and raising the typed
missing-entity error the CLI raises today, message text unchanged.
The API's GETs, the remote CLI (which just asks the API), and the
`--local` recovery `show` all consume the same methods, so
"missing" is decided in one place whatever the transport.

Rendering is presentation, so it moves beside the callers: the
CLI's display helpers (`_provider_data`, `_mcp_data`,
`_layer_data`, the shadow-mark logic) move to a `config/views.py`
module that builds the envelope (plain dicts) from what the
repository returns: the API returns it as JSON, the CLI renders it
as YAML with the comment lines it prints today, and `--local show`
builds it from a locally loaded snapshot through the same
functions. The masking rule stays single-sourced in `secrets.mask`
plus `models.is_secret_option` and `models.is_mcp_secret_key`;
views is the one place it is applied to an entity.

### The OpenAPI document: file, command, version

The committed document lives at `docs/reference/api-openapi.json`,
generated by a new read-only `samtal-server config openapi` command
that builds the sub-application (no database, no configuration file,
no key: the store dependency is never resolved) and renders its
document. CI regenerates and diffs it in the same step pattern as
the markdown reference, and the workflow's existing
`docs/reference/**` path filter already covers it. The same
comparison is a unit test, plus a double-render test pinning
determinism.

FastAPI's default generation describes none of what this API
actually is, so the rendering is explicit about four things:

- **Responses are typed transport models**, defined in `api.py`:
  the read envelope (`entity` as a loose object plus the
  stored-secret map), the identity-keyed list mappings, the write
  acknowledgement (`wrote`, `notice`), and the error shape
  (`detail`). Declared as `response_model` per route, they are what
  registers real response schemas under `components` instead of
  the empty objects untyped dict returns would produce. They are
  shapes, not a second semantics layer: the masked dicts `views`
  builds validate through them unchanged.
- **Request schemas are registered, not just referenced.** Because
  bodies are raw objects at runtime (the no-leak decision above),
  the entity models are absent from FastAPI's own component
  collection, and a bare `openapi_extra` `$ref` would dangle. The
  `openapi()` override injects each entity model's
  `model_json_schema(ref_template="#/components/schemas/...")`
  output, nested `$defs` hoisted, into `components.schemas`, and
  the `openapi_extra` request bodies reference those. A unit test
  walks every `$ref` in the document and asserts it resolves.
- **The mount prefix is represented.** A mounted sub-application
  renders its internal paths (`/config`, not `/api/config`), so
  the document carries `servers: [{"url": "/api"}]`, which is the
  OpenAPI way of saying exactly that; the drift test asserts it.
- **The bearer scheme is stated.** Enforcement lives in the
  middleware (below), so the scheme does not fall out of a
  dependency; the override adds the `securitySchemes` entry and
  the document-level `security` requirement explicitly.

The document's `info.version` is a fixed API version string (`"1"`),
not the package version: a package release does not change the API
contract, and a committed document that rewrote itself on every
version bump would make the drift check cry wolf. The description
states the honest-but-loose provider options contract
(`extra="allow"` until #88) in the same words the markdown
reference uses. The unit suite validates the committed document
with `openapi-spec-validator` (Apache-2.0, dev dependency), so
"generates" means "generates a document a client generator will
accept", not "generates JSON".

### How the CLI finds the server

The CLI needs a base URL and a token. The base URL is `--api-url`,
then `SAMTAL_API_URL`, then the default
`http://127.0.0.1:<server.port>` with the port read through
`load_file_config` (the same machinery that today gives the CLI its
database directory, so the CLI and the server cannot disagree about
the port either). The token is read from the environment variable
`server.api.secret_env` names, from the same file config, which on a
deployment is exactly the variable the server itself was started
with: exec into the running container and the CLI has the token
and the loopback address for free, which is the deployment story
decision 4 wants. A missing token is a `ConfigError` naming the variable before
any request is sent.

HTTP transport is `httpx`, which is already a core dependency (the
cloud providers speak their APIs over it), so the client adds no
dependency at all. The client's timeout policy is explicit, because
the default would lie: the server holds a write for up to the
database's 10 second busy timeout before answering the retryable
409, and httpx's 5 second default would turn exactly that answer
into a client-side timeout, replacing the settled "nothing was
changed; run the command again" with a transport error. The client
uses a bounded connect timeout (5 s) and a read timeout with margin
above the busy timeout (30 s); an acceptance test holds a real
write lock long enough for the API to answer 409 and asserts the
CLI prints that exact detail and exits 1.

The client is built behind an injected-factory seam the tests
replace, and the replacement is named because the obvious one does
not work: `httpx.ASGITransport` is async-only and cannot be mounted
into a synchronous `httpx.Client`, and `cli.main()` is and stays
synchronous. The factory returns an `httpx.Client`; the tests
inject Starlette's `TestClient`, which is itself a synchronous
`httpx.Client` subclass that drives an ASGI app through its own
portal, so the acceptance suite calls the unchanged synchronous
entry point against the real app with no socket and no event-loop
bridging of its own. That is what turns the CLI scenario tests
into the acceptance suite: the same commands, driven through CLI
parsing, real HTTP semantics, the real handlers and the real
repository. Error handling is
symmetric with today: a non-2xx response's `detail` is printed to
stderr verbatim (it is the repository's own message) and the exit
code is 1; a connection failure names the URL and suggests checking
that the server is running or using `--local` if this is recovery.
A response whose body is not the expected JSON shape (a proxy's
error page, say) is reported as the status code and a generic
sentence, never by printing the body: what a middlebox returns is
not this API's sanitized output and does not get relayed as if it
were.

The transport policy protects the token, not only the secret
bodies: the bearer token crosses every request and grants
everything the API can do, including secret writes, so
loopback-or-TLS is the rule for the whole client, not a `set-secret`
footnote. The client refuses a plain `http://` URL whose host is
not a loopback address, naming TLS, a tunnel, or exec-into-the-
container as the ways forward; there is no override flag, because
an override would be a switch whose only purpose is sending the
token in clear. A URL carrying userinfo is refused outright (a
token does not belong in a URL), and transport errors print the
URL with any userinfo stripped, so a mistake cannot leak through
its own error message.

### The first start reverses: start empty, configure, restart

Once the CLI writes through the API, configuring requires a running
server. That works because an empty domain half is a valid boot: the
completeness check only fires when agents exist, so a fresh database
boots a server that serves no agents, the operator configures it
over the API, and a restart picks the configuration up. Getting
Started reorders to exactly that (start, configure, restart), which
is the same procedure a remote deployment uses, and the restart step
the #102 review removed comes back as a documented, deliberate step
rather than a forgotten one.

The smoke lane follows the same shape without changing the
workflow's structure: each seeding script (`seed.sh`,
`seed-slim.sh`, `seed-local-engines.sh`) now starts the server in
the background inside the seeding container, polls `/healthz`, runs
its `config set` commands against loopback through the image's own
CLI, and stops the server; the volume then holds the seeded database
the real container boots from. The seeding still exercises the
shipped artifact, now including the API path, which is the
deployment procedure rather than a fixture. The workflow's image
jobs gain a throwaway `SAMTAL_API_SECRET` beside the existing
`SAMTAL_AUTH_SECRET`.

The scripts fall into two classes with one lifecycle each, and the
tests exercise each class's documented invocation rather than a
fixture-only variant:

- **Self-managed: the smoke seeding scripts.** `seed.sh`,
  `seed-slim.sh` and `seed-local-engines.sh` own their server's
  lifecycle as described above: start, poll, configure over
  loopback, stop. The port comes from the environment
  (`SAMTAL_SERVER__PORT`) with the default as fallback, so a test
  run and a CI container can both pick a free one. Their tests
  (today `tests/unit/test_smoke_seeds.py`) move to the integration
  lane and run each script exactly as CI does, unmodified, against
  a scratch database directory; no fixture serves them, because
  the script's own lifecycle is the thing under test. Assertions
  move unchanged.
- **Against a running server: the deployment profile.**
  `config.deploy.example.sh` documents a procedure that no longer
  exists (run the CLI before the server starts); it is rewritten
  for the API era: exec into the running container, where the
  token variable is already in the environment and the server is
  on loopback, and run the script; `SAMTAL_API_URL` overrides the
  target for running it from outside. Its test moves to the
  integration lane, backed by one new conftest fixture that serves
  a built app on an ephemeral loopback port, and runs the script
  verbatim with `SAMTAL_API_URL` pointed at the fixture, which is
  the documented outside-the-container invocation; the measured
  values and the allowlist are then asserted on the composed
  snapshot as today.

The fragment-driven cases in `test_config_examples.py` (one CLI
command per example file) stay unit tests through the injected
test-client seam, no socket involved.

## Module layout

```
samtal_server/config/
    api.py          build_api(): the sub-application, routes, the
                    bearer dependency, exception handlers, the
                    per-request store dependency
    views.py        the masked envelope of an entity or a snapshot,
                    moved out of cli.py, consumed by api and cli
    cli.py          unchanged grammar; backend swapped to the API
                    client, plus the --local recovery subset
    store.py        unchanged semantics; refusals gain types
                    (UnknownEntityError, DatabaseBusyError,
                    StorageError, all subclassing ConfigError)
    docgen.py       gains the OpenAPI rendering next to schema and
                    reference
    loader.py       gains the typed refusals beside ConfigError
                    (UnknownEntityError, DatabaseBusyError,
                    StorageError), importable by store and db alike
```

`app.py` mounts the sub-application and resolves the API token with
the same fail-at-boot shape as device auth. `models.py` gains
`ApiConfig` on `ServerConfig`. `db/__init__.py` raises the typed
busy and storage errors instead of plain `ConfigError`, message
text unchanged. Nothing moves in `secrets.py` or `boot.py`.

## The API surface

One noun per entity kind, PUT as create-or-replace matching the
CLI's `set`, identity in the path the way the entity is keyed (a
provider is `(stage, name)` everywhere it is named):

```
GET    /api/config                              the whole masked domain document

GET    /api/providers                           mapping: stage -> name -> envelope
PUT    /api/providers/{stage}/{name}            body: fragment
GET    /api/providers/{stage}/{name}
DELETE /api/providers/{stage}/{name}
PUT    /api/providers/{stage}/{name}/secrets/{slot}    body: {"secret": "..."}
DELETE /api/providers/{stage}/{name}/secrets/{slot}

GET    /api/mcp-servers                         mapping: name -> envelope
PUT    /api/mcp-servers/{name}                  body: fragment
GET    /api/mcp-servers/{name}
DELETE /api/mcp-servers/{name}
PUT    /api/mcp-servers/{name}/secrets/{slot}   slot: env.<KEY> or headers.<KEY>
DELETE /api/mcp-servers/{name}/secrets/{slot}

GET    /api/agents                              mapping: name -> envelope
PUT    /api/agents/{name}                       body: fragment
GET    /api/agents/{name}
DELETE /api/agents/{name}

GET    /api/agent-defaults
PUT    /api/agent-defaults                      body: fragment

GET    /api/devices                             mapping: mac -> envelope
PUT    /api/devices/{mac}                       body: {"agents": [...]}
GET    /api/devices/{mac}
DELETE /api/devices/{mac}

GET    /api/default-agent                       {"name": "..." | null}
PUT    /api/default-agent                       body: {"name": "..."}
DELETE /api/default-agent                       clear; idempotent, like the CLI
```

Every successful write answers 200 with
`{"wrote": "<what>", "notice": "<the restart sentence>"}`, reusing
`cli.RESTART_NOTICE` so decision 5's contract is one string in one
place. Deletes answer the same shape. Secret slots ride in the path
because a slot name is an identifier, never a value; the plaintext
rides only in the `set-secret` body, which is why loopback-or-TLS is
a stated deployment requirement.

There is no `/api/schema`: the committed OpenAPI document is the
machine-readable contract, and `config schema` remains for the
model-level JSON Schema.

## Authentication

The gate is ASGI middleware on the sub-application, not a FastAPI
dependency, because a dependency only runs for a matched route: an
unmatched path inside `/api/` would answer 404 to an
unauthenticated caller, which both leaks which routes exist and
breaks "the namespace is gated" as a property. The middleware runs
before routing, so every request under the mount, matched or not,
must carry `Authorization: Bearer <token>`, compared with
`hmac.compare_digest` against the value of the variable
`server.api.secret_env` names, resolved once at app build inside
the fail-at-boot check. Missing or wrong answers 401 with a
`WWW-Authenticate: Bearer` header and a body that says how to
authenticate, never whether the token was close; only an
authenticated caller can tell a route from a 404. The mount is
registered so that both `/api` and `/api/` resolve rather than
relying on a redirect a client may not follow with its
authorization header intact.

Because enforcement is middleware, the bearer scheme does not fall
out of a security dependency; the OpenAPI override states it
explicitly (see the document section). The token is never logged;
the existing log discipline (no headers in events) already holds
and a test pins it for the API path. The milestone 1 acceptance
stands as written: 401 without the token for anything under
`/api/`, 404 with it while no routes exist.

## PR structure

Every push to `main` publishes an image (the workflow's publish
step is gated on `main`, not on anything rarer), so every merge in
this stack is a release, and the structure is chosen so each one is
a valid release: no published state may carry two co-equal write
paths (decision 2), and no published state may require an
environment variable its own smoke lane does not set.

Four PRs, stacked and each independently green (rebase-merge only;
CI runs lint, unit and integration on every `samtal-server/**` and
`docs/reference/**` change), each with its CHANGELOG entry, each
landing its implementation-doc section in the change that ticks its
milestone:

1. **Plan and API skeleton** (branch `feature/rest-api`): this plan;
   `ApiConfig` and the fail-at-boot token; the mounted
   sub-application with the auth gate and the exception handlers;
   the typed refusals; `config openapi`; the committed document and
   its CI drift step. The workflow environment
   (`SAMTAL_API_SECRET` beside `SAMTAL_AUTH_SECRET` in both image
   jobs) and the autouse test fixtures land in this same PR,
   because this is the commit that makes the secret mandatory: the
   PR's own smoke lane must boot, and the image published from its
   merge must be deployable with the documented variable. After
   this merge the release serves an API that answers 401 without
   the token and has no routes.
2. **Read routes** (`feature/rest-api-m2`): the repository read
   methods; `views.py` extracted from the CLI's display helpers;
   every GET including `/api/config`; the transport response
   models and request-schema registration; the document
   regenerated. After this merge the release serves masked reads
   over HTTP, and the CLI is still the one and only write path:
   reads are not a write path, so decision 2 holds.
3. **Write path and CLI switchover** (`feature/rest-api-m3`): every
   write route (entities, devices, default-agent, and the
   write-only secret endpoints) and the CLI's backend swap in the
   same PR, deliberately: the HTTP write path and the CLI becoming
   its client land in one push, so no published state ever holds
   two co-equal write paths. With them, everything the swap
   forces: `--api-url` and token resolution, `--local` with the
   recovery subset and its notice, the scenario tests converted to
   the acceptance suite, the smoke seeding redesign, the script
   tests moved to the integration lane, and Getting Started
   reordered. The largest PR of the stack, the same shape as #86's
   switchover milestone, and for the same reason: the behavior
   change is one reviewable whole.
4. **Docs** (`feature/rest-api-m4`): the server README's API
   section, deployment notes (token generation, ingress guidance
   for `/api/`, loopback-or-TLS, the upgrade note), the reference
   regenerated with its API pointers, root README.

Sequenced so a pause after any merge leaves `main` releasable:
after 1 the API surface exists and is gated, after 2 it reads,
after 3 there is one write path plus the recovery subset, after 4
the issue is done. The issue's five checklist items map onto the
stack as: skeleton to PR 1, entity routes to PRs 2 and 3, secret
routes and the CLI refactor to PR 3, docs to PR 4.

The stacked-PR trap from #86 is procedure here: every child PR is
retargeted to `main` before its parent merges (a rebase merge that
deletes the base branch auto-closes stacked children unrecoverably),
and each child rebases with `git rebase --onto` after each merge.

## Risks and mitigations

- **FastAPI's own machinery leaking rejected input.** Its default
  422 echoes the offending value, and a fragment can carry a pasted
  secret. Mitigation: bodies are raw objects validated only in the
  repository, the `RequestValidationError` handler is overridden and
  sanitized, and the leak tests assert over response bodies for
  exactly the malformed-fragment and inline-secret cases.
- **A new mandatory environment variable breaks every deployment
  and test.** `SAMTAL_API_SECRET` unset refuses the boot from
  milestone 1 on. Mitigation: the autouse conftest fixtures and the
  workflow's image-job environment land in milestone 1 itself, the
  same PR that makes the secret mandatory, so its own CI is the
  proof; the CHANGELOG and deployment notes carry the upgrade step;
  the boot error names the fix, `auth.py`-style. The deployed
  cluster needs the variable before the next image rollout, and the
  memory note carries that.
- **Seeding scripts that boot a server can flake.** Mitigation: the
  scripts poll `/healthz` with a bounded loop and print the server
  log on failure, the same discipline the workflow's health waits
  already use; locally they run in the integration lane where the
  same fixture pattern is exercised on every push.
- **The committed OpenAPI document churns or drifts.** Mitigation:
  fixed `info.version`, deterministic generation pinned by a
  double-render test, the same CI diff pattern that already guards
  the markdown reference, and the document regenerated in every
  milestone that touches routes.
- **The CLI's failure text changes shape behind HTTP.** The API
  carries repository messages verbatim in `detail` and the CLI
  prints `detail` verbatim, so the words survive; the acceptance
  suite asserts the exact stderr text of the converted scenarios,
  which is the regression net for the whole contract.
- **Plaintext over the wire.** `set-secret` over the API sends the
  secret in a request body, and the bearer token rides every
  request. Mitigation is defaults plus a refusal: the CLI defaults
  to loopback, refuses remote plain `http://` outright, and the
  deployment notes require loopback-or-TLS for the API as a whole;
  the API never logs bodies or authorization headers.
- **A published state with two write paths.** The workflow
  publishes an image on every push to `main`, so "the stack merges
  as one train" is not a mechanism, it is a hope. Mitigation is
  structural: the HTTP write routes and the CLI's conversion to
  their client land in the same PR, so no push to `main` ever
  holds both a writable API and a locally writing CLI.
- **The stale bytecode trap** (AGENTS.md) during manual runs:
  `PYTHONDONTWRITEBYTECODE=1` outside pytest, and suspect the cache
  before the code when a result contradicts the source.

## Plan review round

One external review of the plan as first committed (5029091): codex
CLI 0.147.0, model gpt-5.6-sol, read-only against this repository
with the issue #101 body supplied, 2026-08-11. Verdict: ready after
the P1 and P2 amendments, not ready to implement as is. Findings as
received, condensed; each carries its resolution once the amendment
addressing it lands.

1. **P1: the stacked PR sequence would publish forbidden
   intermediate releases.** The plan assumes no image is published
   between milestones, but the workflow publishes after every push
   to `main`, and separate rebase merges are separate pushes: a
   published image between the entity-routes and CLI milestones
   carries two co-equal write paths, which decision 2 forbids a
   release to ship. Milestone 1 would also make the API secret
   mandatory before the workflow passes it into the smoke
   containers, so its own CI would go red. Land milestones 1
   through 4 as one implementation PR, or restructure so every
   push to `main` is a valid release, and give every
   server-starting `docker run` the secret from the first commit
   that requires it.
   *Resolution*: the stack is restructured to four PRs so every
   merge is a valid release: skeleton (gated API, no routes), read
   routes (reads are not a write path), then the write routes and
   the CLI conversion in one PR so no published state ever holds
   two co-equal write paths, then docs. The workflow's
   `SAMTAL_API_SECRET` and the autouse test fixtures move into
   milestone 1, the PR that makes the secret mandatory, with its
   own smoke lane as the proof; the PR-structure section now opens
   with the publish-on-every-push fact, and the two-write-paths
   risk entry names the structural mitigation instead of a hoped
   merge train.
2. **P1: legal repository identities and secret slots are not
   addressable by the proposed paths.** The repository accepts any
   non-blank provider or agent name and slot rules permit keys
   containing `/`; a decoded slash changes routing, so such
   entities cannot be fetched, deleted, or have secrets managed
   over the proposed paths. Choose an addressing scheme that
   represents every repository-valid string, or change what the
   repository accepts, with acceptance cases for `/`, `%`, spaces,
   Unicode, and dotted slot names.
   *Resolution*: the repository's write path gains an
   addressability rule (a new "Identities must survive a URL path"
   section): names and slots must be expressible as one URL path
   segment, with the MCP slot halves constrained to what an env
   reference or an HTTP header could ever name. A semantics-layer
   change inherited by both callers, applied at write time only,
   so pre-existing unaddressable rows still boot, still show in
   the whole-config reads, and remain deletable through
   `--local`. Acceptance tests round-trip `%`, spaces, Unicode
   and dotted slots, and pin the write-time slash refusal.
3. **P1: the typed 409/500 mapping cannot cover failures from
   per-request database opening.** Every request first calls
   `open_database()`, which performs a `BEGIN IMMEDIATE` migration
   check and collapses every failure into plain `ConfigError`, so
   a lock timeout during the open becomes 422 rather than the
   settled 409. Put the typed storage exceptions in a neutral
   module, raise them from both `open_database()` and
   `ConfigStore._transaction()`, and test contention in both
   phases asserting the status without message parsing.
   *Resolution*: the typed refusals move to `loader.py` beside
   `ConfigError` (no database imports, so `db/` can raise them),
   `open_database()` maps its lock timeout and residual failures
   to the same busy and storage types the repository uses with
   message text unchanged, and the unit tests force the 409 twice,
   once inside the open-and-migrate step and once inside a
   repository write, asserted by status code alone.
4. **P1: `secret_env` repeats an existing pasted-secret leak.** The
   plan types `ApiConfig.secret_env` as a non-blank string and then
   quotes it in the boot failure; `AuthConfig.secret_env` has the
   same hole today, while provider `*_env` fields already reject a
   pasted value without quoting it. An operator who pastes the
   token where its variable name belongs gets it printed by the
   boot error. Define a shared validated environment-variable-name
   type, use it for the API and device auth, and refuse invalid
   values without quoting them, with sentinel tests over stderr,
   logs, and exception chains.
   *Resolution*: adopted in full; the `server.api` section now
   defines a shared `EnvName` annotated type on the models,
   enforcing the existing `_ENV_NAME_RE` rule for `api.secret_env`
   and `auth.secret_env` both, refusing without quoting, with the
   provider validator's wording precedent and sentinel tests over
   stderr, logs, and the exception chain. The behavior change is
   stated: a pasted value in either key never worked, it now fails
   at parse time without echoing the paste.
5. **P1: the proposed OpenAPI generation does not describe the
   deployed contract.** `openapi_extra` does not register pydantic
   models and their nested definitions under `components`, untyped
   dict responses produce weak or empty response schemas, and a
   mounted sub-application generates internal paths (`/config`)
   rather than the externally mounted ones (`/api/config`). Name
   transport response models, specify how request models and
   nested `$defs` are registered, represent the mount prefix
   (`servers`), and validate the generated document with an
   OpenAPI validator rather than only checking schema names.
   *Resolution*: the OpenAPI section now names the transport
   response models (envelope, list mappings, acknowledgement,
   error) declared as `response_model`, specifies the `openapi()`
   override that injects the entity models' schemas with hoisted
   `$defs` into `components` for the `openapi_extra` request
   bodies to reference (with a test resolving every `$ref`),
   carries `servers: [{"url": "/api"}]` for the mount prefix, adds
   the bearer scheme explicitly since enforcement moved to
   middleware, and validates the committed document with
   `openapi-spec-validator` as a dev dependency.
6. **P2: missing-entity reads would recreate semantics outside the
   repository.** `ConfigStore` only exposes a whole-snapshot
   `load()`; single-entity reads and their "no such" refusals live
   in the CLI today, and moving only rendering into `views.py`
   leaves existence decisions outside the repository. Add
   repository read methods per addressable entity, returning the
   entity plus its secret metadata or raising the typed
   missing-entity error, consumed by the API, the remote CLI, and
   local recovery alike.
   *Resolution*: adopted; the views section is now "one masked
   view, two renderings, and repository-owned reads":
   `ConfigStore` gains a read method per addressable entity kind
   returning the entity with its stored-secret slots or raising
   the typed missing-entity error with today's message text, and
   the API, the remote CLI, and `--local show` all consume them,
   with `views.py` holding presentation only.
7. **P2: application-level dependencies cannot satisfy the
   skeleton's authentication acceptance test.** FastAPI app-level
   dependencies run for matched routes, not for an unmatched 404,
   and `/api` may redirect to `/api/` before the sub-application
   handles it, so "401 without a token, 404 with one, before any
   routes exist" cannot pass as designed. Gate the namespace with
   authentication middleware around the mounted application, or
   defer the acceptance test until a real route exists.
   *Resolution*: the gate is ASGI middleware on the
   sub-application, running before routing so unmatched paths are
   401 to an unauthenticated caller too (an unauthenticated 404
   would also leak which routes exist); the mount resolves both
   `/api` and `/api/` rather than relying on a redirect; the
   bearer scheme moves into the explicit OpenAPI override since no
   dependency carries it; the milestone 1 acceptance stands.
8. **P2: secret request-body validation is omitted and can persist
   malformed encrypted state.** The plan names only the device and
   default-agent writes as handler-side extraction, but the secret
   routes also parse `{"secret": ...}`, and
   `ConfigStore.set_secret()` trusts its annotation: a non-string
   or empty value could be encrypted and then fail boot
   verification. Move the non-empty-string invariant into the
   repository, parse the API body through a sanitized exact-shape
   parser, and leak-test every malformed-body path with sentinel
   values.
   *Resolution*: adopted; the request-body section now counts the
   secret write among the argument-shaped routes with an
   exact-shape sanitized parser (missing, extra, null, non-string
   and wrong-container each refused without echoing), and
   `ConfigStore.set_secret` itself refuses a value that is not a
   non-empty string, so an envelope that would fail the next
   boot's verification cannot be created by any caller.
9. **P2: the HTTP client can time out before the required 409
   exists.** SQLite waits 10 seconds for the write lock and
   httpx's default timeout is shorter, so the CLI can report a
   transport timeout instead of the settled retryable 409. Set an
   explicit read timeout above the busy timeout with margin, and
   hold a real write lock in an acceptance test asserting the CLI
   prints the 409 detail.
   *Resolution*: adopted; the client section now fixes connect at
   5 s and read at 30 s (margin above the 10 s busy timeout), says
   why the default would have lied, and adds the lock-held
   acceptance test asserting the CLI prints the 409 detail and
   exits 1. The same edit corrects a plan error the review did not
   flag: httpx is already a core dependency, not a new one.
10. **P2: the proposed ASGI test seam is incompatible with the
    synchronous CLI as stated.** `httpx.ASGITransport` is an async
    transport and cannot be mounted into a synchronous
    `httpx.Client`, and `cli.main()` is synchronous. Specify an
    injected synchronous client seam (a TestClient-compatible
    client) or a deliberate sync bridge, and drive the acceptance
    suite through the unchanged synchronous entry point.
    *Resolution*: the seam is an injected client factory returning
    an `httpx.Client`; the tests inject Starlette's `TestClient`,
    itself a synchronous `httpx.Client` subclass with its own
    portal, so the acceptance suite calls the unchanged
    synchronous `cli.main()` with no event-loop bridging of its
    own. Every ASGI-transport mention in the plan is corrected to
    the injected test-client seam.
11. **P2: the script migration has two incompatible
    server-lifecycle designs and omits the deployment-profile
    rewrite.** The plan first says every seeding script starts and
    stops its own server, then backs the same script tests with a
    separate served-app fixture; and `config.deploy.example.sh`
    documents a run-before-the-server procedure that cannot reach
    the new loopback API. Define one lifecycle per script class,
    name the deployment-profile rewrite explicitly (how it reaches
    the server, obtains the token, cleans up), and exercise the
    documented invocation rather than a fixture-only variant.
    *Resolution*: the script section now defines the two classes:
    the smoke seeds are self-managed (start, poll, configure,
    stop, port from the environment) and their integration tests
    run them unmodified with no fixture, because the lifecycle is
    the thing under test; `config.deploy.example.sh` is rewritten
    to run against a running server (exec into the container where
    token and loopback are ambient, `SAMTAL_API_URL` to run it
    from outside) and its integration test runs it verbatim
    against the served-app fixture through exactly that override.
12. **P2: the transport policy protects secret bodies but not the
    bearer token itself.** The CLI permits an arbitrary remote
    `--api-url` while the security guidance requires
    loopback-or-TLS only for `set-secret`; the reusable token
    crosses every connection and grants secret writes. Require TLS
    for every non-loopback request (preferably a client-side
    refusal of remote `http://`), reject URLs containing userinfo,
    sanitize URLs in transport errors, and handle non-JSON error
    responses with a generic message.
    *Resolution*: adopted in full; the client refuses remote plain
    `http://` with no override flag, refuses URLs carrying
    userinfo, strips userinfo from URLs in error messages, and
    reports a non-JSON error response as a status code plus a
    generic sentence rather than relaying a middlebox's body; the
    deployment notes state loopback-or-TLS for the API as a
    whole, not only for secret writes.
13. **P3: the documentation names a specific deployment platform
    contrary to repository convention.** The plan's deployment
    story says `kubectl exec` and "pod"; AGENTS.md requires
    deployment documentation to stay generic. Say "exec into the
    running container" and leave orchestration commands out.
    *Resolution*: adopted; the plan and the documentation it
    prescribes say "exec into the running container", and no
    orchestrator is named anywhere in the deliverables.
