# Turn the CLI around and make its default install thin

Issue #223, re-cut after the 2026-08-24 architecture ruling and after
#281 and #282 removed the local-database path. Fourth substantive issue
of the #265 CLI chain. Deviations, resolutions and discoveries land in
the companion `2026-08-24-cli-recut-implementation.md`, one section per
milestone, appended in the change that ticks the milestone.

This plan supersedes the parked `2026-08-24-standalone-cli.md` (branch
`feature/standalone-cli`, tip `2e0ad088`, draft PR #280). That document
stays where it is as the record of the round that produced twelve
amendments this plan carries; nothing on it is ticked and nothing on it
merges.

## Goal

Two things, in one issue because they rewrite the same surface.

**The grammar turns around.** `vinga-server config set provider llm
local` becomes `vinga provider set llm local`, per the noun-verb
decision and the practices #285 wrote down in
`docs/architecture/cli-guide.md`. Every command word in the grammar is
respelled once, every generated document moves once, and
`docs/reference/events.md` moves with them as a deliberate artifact
change.

**The default install becomes the client.** An operator on a laptop
runs

```bash
uvx --from "git+https://github.com/rafacm/vinga#subdirectory=vinga-server" vinga
```

and gets pydantic, pydantic-settings, httpx, typer, PyYAML and
python-dotenv, and NOT FastAPI, SQLAlchemy, Alembic, cryptography, the
LLM SDKs or the audio stack. Serving moves behind a `[serve]` extra.
The #265 chain's wheel-grade acceptance lane lands with it: the built
wheel installed bare into a clean venv and the actual `vinga` binary
driven as a subprocess against a live server, inventory-complete.

## The settled decisions, restated

These are ruled, not reopened here. They are restated because a plan a
fresh session reads has to carry its own premises.

1. **One distribution.** `vinga-server` stays the only package. Its
   default install is the thin client; `[serve]` carries the server.
   No `vinga-cli` package is created here. Ruled by the maintainer on
   2026-08-24 (late), on verified ecosystem research: across Prefect,
   FastAPI, Airflow, Sentry, Home Assistant, HashiCorp, PocketBase,
   Docker, Kubernetes, OpenStack and mlflow, no project has a server
   import its domain models from a CLI package; the pre-1.0 norm is the
   single artifact; and the graduation path for a standalone CLI is a
   client generated from the committed OpenAPI contract, which is
   exactly the artifact this repository already maintains under CI
   drift.
2. **Structured for the pattern-3 exit, which is #287.** The CLI is a
   clean internal module whose boundary is held by import-weight tests
   rather than by packaging; its types stay behind the shapes an
   OpenAPI-generated client would emit; the server never imports from
   the CLI's territory. #287 is filed with an explicit trigger (after
   #190 and #129 stabilize the API surface, or at first publication,
   whichever comes first). This plan STRUCTURES for that exit and does
   not take it.
3. **The three doors.** Operators run the image through docker compose.
   Laptop users run the CLI through `uvx --from git+...`, with no
   publication step and no published name. Contributors run the
   checkout: `cd vinga-server && uv sync` keeps yielding a runnable
   server with no new flags, and the AGENTS.md Commands section does
   not change.
4. **The grammar is noun-verb, per `cli-guide.md`.** The rename moves
   `docs/reference/events.md` deliberately, because the shipped event
   messages pin the full `config bind-device` and `config add-device`
   spellings. The `vinga` console script drops the `config` dispatch
   word; both spellings resolve (`vinga provider set ...` and
   `vinga-server config provider set ...`).
5. **The simulator comes after.** #248 lands `vinga sim` as a
   subcommand of this package behind a `[sim]` extra. This plan leaves
   it room (the extras mechanism, the noun-verb tree, the subprocess
   lane it will extend) and designs nothing for it.
6. **Merge-on-green is authorized**, and the plan PR itself is
   published for the maintainer's record.

## Decisions

### 1. Three milestones, and the rename goes first

The binding constraint is that every merge to `main` is releasable,
because the image publishes on every push. Both orders satisfy it, so
the cut is decided on diff legibility and artifact churn.

**The rename is ONE milestone, not staged.** Staging it would either
move `events.md` twice or leave `main` carrying a half-renamed grammar
between merges, which is two co-equal grammars for one command group:
the shape #194's plan (decision 10) already refused to merge, for the
same reason. One milestone, one artifact move.

**The rename goes before the tiering**, for four reasons.

- **One artifact churn.** The rename rewrites every command word, and
  the console script rewrites the program word in front of every
  command word. Both regenerate `cli.md`, `domain-config.md`,
  `api-openapi.json` and `events.md`. Landing them together means the
  spelling surface moves once; landing them apart means a reviewer
  reads a full-tree regeneration diff twice.
- **Diff legibility.** With the rename first, the tiering milestone's
  diff is about dependencies and import sites and nothing else.
- **Pin-before-reshape needs a stable dependency graph.** The rename is
  proven behavior-preserving by differential tests (decision 14).
  Re-tiering underneath a rename would make a differential failure
  ambiguous between "the spelling moved" and "an import went lazy".
- **If the run is interrupted**, a fully renamed grammar is a coherent
  state and a half-tiered package is not.

The counter-argument, recorded: the issue's headline value is the thin
install, and putting it second delays it by a milestone. Accepted,
because a milestone is the unit of delay and the argument above is paid
in every review of both.

### 2. The grammar, in full

Nouns are the configuration's own words. The five entity kinds come
from `entities.ENTITIES` and their four core verbs are generated from
it, exactly as today. What follows is the whole respelled tree, which
is also M1's acceptance list.

**Derived per kind** (`provider`, `mcp-server`, `prompt-fragment`,
`agent`, `agent-defaults`), addressing unchanged because it is read off
the descriptor's `addressing` tuple:

| Today | After |
| --- | --- |
| `set <kind> [address] ...` | `<kind> set [address] ...` |
| `delete <kind> [address]` | `<kind> delete [address]` |
| `show <kind> [address]` | `<kind> show [address]` |
| `export <kind> [address]` | `<kind> export [address]` |

**Written out**, one row per command word that is not derived:

| Today | After | Why |
| --- | --- | --- |
| `bind-device <mac> <agent>...` | `device bind <mac> <agent>...` | the guide's own resolution of tension #61 |
| `add-device <code> <agent>...` | `device pending claim <code> <agent>...` | `claim` is this repository's own word for the act (`onboarding/pending.py`: "devices waiting to be claimed", "its claim lifecycle"), and it makes the pair semantically distinct instead of distinguishable only by help text |
| `pending` | `device pending list` | see decision 4 |
| `show device <mac>` | `device show <mac>` | |
| `delete device <mac>` | `device delete <mac>` | |
| `set-secret provider <stage> <name> <slot>` | `provider secret set <stage> <name> <slot>` | see decision 4 |
| `clear-secret provider <stage> <name> <slot>` | `provider secret clear <stage> <name> <slot>` | |
| `set-secret mcp-server <name> <slot>` | `mcp-server secret set <name> <slot>` | |
| `clear-secret mcp-server <name> <slot>` | `mcp-server secret clear <name> <slot>` | |
| `set-default-agent <name>` | `default-agent set <name>` | the setting is a noun with two verbs; `<name>` is payload, not address, because `/default-agent` has no path parameter |
| `clear-default-agent` | `default-agent clear` | |
| `prompt <agent>` | `agent preview <agent>` | decision 3 |

**Flat, unchanged**: `apply`, `export`, `show`, `list`, `reload`,
`status`, `ota-url`, `schema`, `reference`, `openapi`,
`cli-reference`, and the new `diff`. The whole-deployment forms of
`show` and `export` stay flat beside their per-noun forms, which the
guide blesses explicitly.

`status` staying flat is a decision and not an omission. Its subject is
the running server, the same subject `reload` has, and the pair is the
deployment's runtime pair; that its rows happen to be MCP servers is a
fact about the report, the way `list`'s rows happen to be kinds. The
alternative, `mcp-server status`, was rejected because `status` is not
a verb and the noun would then carry one read with an identity (`show
<name>`) and one without, which is the asymmetry noun-first exists to
remove.

`diff` is seated flat with the others, per the guide's own sentence
naming it beside `apply`, `export` and `reload`. Its deliverables are
the parked plan's: the typed response shapes the committed document
already carries, the act, a renderer in the house listing style,
registration and help, with live-lane, wheel-lane and refusal coverage.

### 3. The `prompt` open case resolves to `agent preview <name>`

The guide records `prompt` as its one open case: it is a noun in the
verb slot, `agent prompt kids` reads as a possessive, and either it
earns an exception or it gets a verb. **It gets a verb**, and the verb
is `preview`.

The reasoning, in the order it is checked:

- **A verb slot holds a verb**, so the exception is not taken. Taking
  it here would make the rule unenforceable at the first command that
  asked, and `pending` and `status` are both queued behind it.
- **`preview` is this repository's own word for the act.** The design
  guide, describing this exact route, says "The operator-facing read,
  `GET /runtime/agents/{name}/prompt`, is a separate interface with a
  separate job. **It previews what an agent would be sent.**" The
  guide's noun rule ("a noun is the configuration's own word for the
  thing") applied to the verb slot gives `preview` without inventing
  anything.
- **It pairs with `show`.** `agent show kids` prints what is stored;
  `agent preview kids` prints what a new session would be sent. Stored
  against assembled is a real distinction an operator has to make, and
  two verbs on one noun is what noun-first is for.
- **It adds no third tree level.** The runner-up, `agent prompt show
  kids`, would introduce a sub-noun for a sub-thing with exactly one
  verb; decision 4 says when that is earned, and this is not it.

The ambiguity objection ("preview what?") is answered by the help
string and by the fact that an agent has exactly one previewable thing.
Recorded as this plan's resolution of the guide's open case, and the
guide's paragraph is rewritten in M1 to state it as settled.

### 4. Tree depth is derived from the API's own paths

Two commands need a sub-noun level, and inventing a rule per command is
how the old grammar got two shapes for one relationship. The rule is
derived instead, from the paths the grammar already mirrors:

> **A path segment that is followed by an identity of its own is a
> sub-noun. A trailing segment with no identity after it is an
> attribute of its parent, and reading an attribute is a verb on the
> parent.**

Applied:

- `/providers/{stage}/{name}/secrets/{slot}`: `secrets` is followed by
  `{slot}`, so `secret` is a sub-noun of `provider`, with `set` and
  `clear` as its verbs. Identity depth is three (`stage`, `name`,
  `slot`), which the guide names as the floor of what is needed and
  also the ceiling.
- `/devices/pending/{code}`: `pending` is followed by `{code}`, so
  `pending` is a sub-noun of `device`, with `claim` as its verb. The
  listing `GET /devices/pending` is `list` on the same sub-noun, which
  is what makes `device pending list` a verb command rather than the
  adjective-in-the-verb-slot `device pending` would have been.
- `/runtime/agents/{name}/prompt`: `prompt` is trailing with no
  identity, so it is an attribute, and it becomes a verb on `agent`
  (decision 3).

The rule is stated in `cli-guide.md` in M1, in the grammar section
beside identity addressing, with these three as its worked cases. It is
the guide's "the grammar is derived from the model it addresses" rule
applied to tree depth rather than to row content, which is the one
place that rule was not yet reaching.

### 5. Two spellings, one grammar, and what `COMMANDS` becomes

**During and after, `vinga-server config <noun> <verb> ...` resolves.**
`main.py`'s first-word check on `config` is untouched, and it goes on
handing `sys.argv[2:]` to `cli.main`. What changes under that word is
the tree, not the dispatch. The `config` word keeps its three siblings
(`conversations`, `events`, `doctor`) and its exit-2 root contract.

**`vinga <noun> <verb> ...` is the same `cli.main`**, registered as
`[project.scripts] vinga = "vinga_server.config.cli:main"`. `main`
keeps its `(argv: Sequence[str] | None = None) -> int` signature, which
every acceptance suite monkeypatches around, and defaults `argv` to
`sys.argv[1:]` when it is not given, which is the console-script case.
There is no `vinga config` spelling: the word exists to dispatch away
from serving, and there is nothing to dispatch away from here.

**The registration table changes shape and gains two facts.**
`Command.words` is already a root-first tuple, so a three-word row
(`("provider", "secret", "set")`) needs no new FIELD. It does need new
CODE, in more places than the row type suggests, and decision 5a lists
them, because the draft's claim that it "needs no new structure" was
false and the places it was false in are exactly the places a
completeness test lives. What changes on the table itself:

- `GROUPS` today is a hand-written map of six VERB words to
  descriptions. It becomes a map of NOUN paths to descriptions, and the
  five entity nouns' descriptions derive from their descriptors'
  `title` and `location` through `_about`, the same function the row
  help already comes from. What stays hand-written is the words the
  registry cannot supply: `device`, `device pending`, `default-agent`,
  and the two `secret` sub-nouns. A new entity kind gets a noun with
  its four verbs by existing, which is what it does today for the four
  verb groups.
- `Command` gains `destroys: bool` (decision 7c), so the confirmation
  is driven by a fact on the registration rather than by a list beside
  it. This is the shape #194's decision 5 gave `local_ok`. Unlike
  `local_ok`, its coverage test may NOT be derived from the same fact,
  because the fact is the thing being introduced; decision 7c gives it
  an independent oracle.

**`cli.COMMANDS` stays the public name** the docgen, the live lane, the
wheel lane and the completeness tests read. Nothing external learns a
new import.

### 5a. Two words is assumed in six places, and every one is named

The grammar has never been deeper than two words, and that assumption
is written into more than the registration loop. Every site below is a
place where a three-word row would be silently mis-registered,
mis-resolved or dropped from a coverage set, which is worse than a
crash: a completeness test that cannot see a command reports full
coverage of a tree with a hole in it. Each is named with the
three-word case that must be added beside its existing cases.

- **Registration** (`config/cli.py`, `command()`, lines 3108-3134).
  Today it registers under `row.words[0]` and treats `row.words[-1]` as
  the leaf, so the intermediate `secret` word is discarded and the
  command lands directly under `provider`. It must build the full
  prefix tree from `row.words[:-1]`, creating each intermediate group
  once and attaching the leaf at the end. Case:
  `("provider", "secret", "set")` and
  `("provider", "secret", "clear")` produce ONE `secret` group under
  `provider` carrying two commands.
- **Kind resolution** (`_invocation`, lines 2420-2443). Today
  `kind=row.words[-1] if len(row.words) > 1 else ""`, which would make
  a provider secret command's kind `"set"` and break `_secret_path`.
  Kind stops being derived from position: it becomes an EXPLICIT field
  on `Command`, defaulting to the noun when the row addresses one kind.
  Explicit rather than "the first word", because `device pending
  claim`'s kind is the device kind while its noun path is two words,
  and a positional rule would have to be read backwards to see that.
  Case: `("provider", "secret", "set")` resolves kind `provider`, not
  `set` and not `secret`.
- **The live lane's inventory helper**
  (`tests/integration/test_cli_live.py`, `registered`, lines 237-256).
  It scans for a first word and then tries `argv[index:index + 2]`,
  so it can never match a three-word row and would silently attribute a
  secret command to the bare `provider` row, marking the wrong entry
  driven. It becomes longest-registered-prefix matching over the whole
  table. Case: `provider secret set llm claude api_key` resolves to the
  three-word row and NOT to `("provider",)`.
- **The wheel lane's inventory map** (decision 11), which reads
  `cli.COMMANDS` the same way and must use the same matcher. One
  matcher, in one place, used by both lanes: two implementations of
  longest-prefix matching would be the pending bug the design guide
  names.
- **The refusal inventory**, the per-family representative refusal the
  live lane holds complete against the registration table. Its notion
  of "family" is today's first word; under three-word rows a family is
  the noun path, not the first word, or `provider secret` refusals
  would count as `provider` refusals.
- **The document renderers** (`config/docgen.py` and `cli.py`'s
  `_help_pages`), which walk the tree emitting a page per command and
  a heading per level. A discarded intermediate group means a missing
  heading in the committed reference, which CI would catch as drift
  without saying why. Case: the generated `cli.md` carries a `provider
  secret` section between `provider` and its verbs.

The through-line: the depth assumption is one fact written in six
places, so the amendment is one matcher plus one explicit field, not
six local patches. A test that enumerates `COMMANDS` and asserts every
row is reachable by its own words through the built tree is what makes
a seventh site fail loudly rather than quietly.

### 6. A generated document carries one canonical spelling

The determinism practice says every generated document may never vary
with the terminal. Two console scripts make it also true that a
document may never vary with the INVOCATION, and the recipe renderer
makes that load-bearing rather than tidy.

`docgen._quoted` selects the commands it publishes as recipes by
matching each example file's comment lines against `f"{program} "`. If
`PROGRAM` became invocation-aware and the example files carried one
spelling, then rendering `cli-reference` through the other entry point
would match nothing and publish an empty recipes region, and the CI
drift step would fail on an unrelated change. That is not a bug to be
found later; it is the reason for the rule.

So there are two names, and they are different things:

- **`PROGRAM = "vinga"`**, a constant, is what every generated artifact
  is rendered with: the committed `cli.md` (help pages and recipes),
  the export header and its `set-secret` lines, the reference intro,
  and the `command` strings on the `SETTINGS` descriptors that
  `domain-config.md` renders. The example files' quoted commands are
  respelled to it in M1, and `_quoted` matches that one prefix.
- **The invocation-aware name** is used only for what a live `--help`
  or a live usage sentence prints, and it is a CLOSED map from known
  entry points to two fixed strings (`vinga`, `vinga-server config`)
  with the canonical constant as the answer for anything else. Raw
  `argv[0]` is never interpolated into help, recipes, export output,
  the reference, logs or exception text, and a hostile-`argv[0]`
  sentinel case covers all six surfaces (parked finding 15).

A consequence worth stating, because a reviewer will ask: the committed
`cli.md` shows the `vinga` spelling everywhere after M1, including in
the pages CI renders by running `vinga-server config cli-reference`.
That is correct and intended. `cli.md`'s hand-written head says so once,
in the two-spellings paragraph the guide already models.

### 7a. Every new sentence is a fixed constant, and the sentinels are exhaustive

The plan's first draft had the confirmation prompt name the "resolved
address", on the reasoning that an address is not a credential. That is
wrong twice. The address is still built from caller-controlled `stage`,
`name`, `mac`, `code` and `slot`, which the guide forbids in any
sentence without carving an exception for addresses (`cli-guide.md`,
lines 334-351 and 891-892); and a mistyped command is exactly where a
credential lands in an address field, which is the mistake the guide
names as the one that produces these sentences most often. So:

**Every sentence this issue adds is a fixed constant containing no
address and no other invocation value.** That covers all four new
sentence kinds:

- the destructive confirmation question and the sentence a declined
  confirmation prints;
- the `--no-input` refusal, which is what a destructive verb answers
  when a confirmation would have been required and prompting is
  disabled;
- M2's serve-without-the-extra sentence;
- M2's `openapi`-without-the-extra sentence.

A prompt that cannot name what it is about is a real usability cost,
paid knowingly: the verb and the noun are already on the command line
the operator just typed, and the guide's answer to "which entry is
this" is `show` before `delete`, not a sentence that quotes back what
was typed.

**The sentinels are exhaustive, not representative.** The failure the
reviewer named is a sentinel planted only in a secret body while the
address fields go untested. So each new sentence's case plants a
DISTINCT credential-shaped sentinel in every field that could carry
one, one field per sentinel so a leak names its own source: every
identity segment the command takes (`stage`, `name`, `mac`, `code`,
`slot`), the `-f` path, the `--from-env` variable NAME and its VALUE,
and, for the two extra refusals, the message of the simulated
`ImportError` that triggers them. Absence is asserted on all four
surfaces the existing sentinel cases use: stdout, stderr, the collected
log records rendered whole, and the exception chain.

### 7b. The prompt-control flags, across every prompt and every position

`--no-input` disables EVERY prompt, which is the guide's rule (clig 56)
and not only the confirmation's. The draft's matrix covered the
confirmation alone and said nothing about the prompt that already
exists, `set-secret`'s no-echo read, nor about how a boolean global
survives three callback layers.

**The seam.** `Globals` carries the two options as `bool | None`, not
`bool`, and `merged` folds them with `is not None` exactly as it folds
`config` and `api_url` with `is None` today (`config/cli.py` lines
2328-2336). An ordinary boolean default is the bug: an absent leaf copy
would arrive as `False` and overwrite a root `True`, so `vinga
--no-input agent delete kids` would prompt. Resolution to a plain
boolean happens ONCE, after the final merge, at the decision site. Both
flags are accepted at the root and at the leaf, like the two existing
globals, and the option matrix #194 M1 built is parameterized, so they
inherit its before/after/conflict cases by being added to it.

**The complete precedence matrix**, which is what M1 implements and
tests:

| Situation | Answer |
| --- | --- |
| destructive verb, TTY, neither flag | confirm; declining prints the fixed sentence and exits 1 |
| destructive verb, TTY, `--force` | no prompt, proceed |
| destructive verb, TTY, `--no-input` | no prompt, REFUSE with the fixed sentence and exit 1 |
| destructive verb, TTY, `--force --no-input` | no prompt, proceed. `--force` answers the question `--no-input` would have refused for; the two are not in conflict, and a script that passes both is asking for the same thing twice |
| destructive verb, not a TTY, neither flag | no prompt, proceed. Never block a pipe, which is the automation rule |
| destructive verb, not a TTY, either flag | as above, no prompt, proceed |
| `set-secret`, TTY, no `--from-env`, no `--no-input` | no-echo prompt, as today |
| `set-secret`, TTY, `--no-input`, no `--from-env` | no prompt; read stdin plainly, which is the non-TTY path, and let it fail as an empty value if nothing is piped. It does NOT refuse: `--no-input` disables prompting, and a value is still reachable |
| `set-secret`, `--from-env` given, any TTY state, any flag | read the variable; no prompt was ever going to happen |
| `--no-input` at root, absent at leaf | root value survives, which is what `bool \| None` buys |
| `--no-input` at leaf, absent at root | leaf value applies |
| both positions, differing | leaf wins, like `--config` and `--api-url` |

The one asymmetry worth naming, because it looks like an inconsistency:
`--no-input` REFUSES a destructive verb and does NOT refuse
`set-secret`. The difference is that a confirmation has no other way to
be answered, so disabling it removes the only door, while a secret has
three doors and disabling one leaves two. `--force` is the destructive
verb's second door, which is why the pair proceeds.

### 7c. The destructive set is enumerated here, not derived from itself

`Command.destroys` cannot be its own oracle. A test that derives the
expected set from the flag it is checking passes on a `delete` row
accidentally marked false, because the row leaves the implementation
and the expectation together. So the intended set is enumerated in this
plan, as a closed semantic list, and the test compares that list
against `COMMANDS`, failing in both directions: a row in the list
without the flag, and a row with the flag not in the list.

**Destructive, and therefore confirmed** (eight rows today, and the
count is part of the assertion):

- `provider delete`, `mcp-server delete`, `prompt-fragment delete`,
  `agent delete` (the four kinds with `has_delete`);
- `device delete`;
- `provider secret clear`, `mcp-server secret clear`;
- `default-agent clear`.

The list is stated as "every `has_delete` kind's `delete` row" plus
the four named ones rather than as eight literals, so a fifth deletable
kind does not silently shrink the expectation. A new
entity kind with `has_delete=True` therefore joins both sides at once,
which is the one derivation that is safe here because it comes from the
descriptor registry rather than from the flag.

**Explicitly NOT destructive, with the reason** (this is the half the
reviewer asked to be decided rather than left implicit):

- **Replacement writes.** `<kind> set` overwrites an entity whole, and
  `apply` overwrites many. They are not confirmed, for three reasons.
  The API acknowledges exactly what was written, so the operator learns
  the outcome; the previous value is recoverable by writing it back,
  and `export` is the documented way to have it; and prompting on every
  `set` would put a prompt in the middle of the most-scripted command
  in the grammar, which the automation rule forbids in spirit even
  though `--no-input` would technically satisfy its letter.
- **Rebinding.** `device bind` and `device pending claim` replace a
  board's agent list. Same reasoning: an overwrite the API
  acknowledges, reversible by rebinding, and the pending-claim path is
  the onboarding flow, where a prompt in front of a prompt-shaped
  ceremony is noise.
- **`reload`.** It changes what a server is doing, not what is stored,
  and it is the recovery from a bad write rather than a risk of one.

The line the list draws, stated once so a future command can be held to
it: **a verb is destructive when its effect cannot be undone by running
another command with information the operator still has.** A delete
destroys the body; a `set` does not, as long as an `export` exists.
That is also why `--force` is the destructive verb's second door and
`set` needs none.

### 8. The dependency tiers, and the three doors proven

Core dependencies become exactly what the client needs: `pydantic`,
`pydantic-settings` (the config models import it eagerly and the CLI
imports the models), `httpx`, `typer`, `pyyaml`, `python-dotenv`. A new
`serve` extra carries `fastapi`, `uvicorn[standard]`, `sqlalchemy`,
`alembic`, `cryptography`, `av`, `mcp`, `openai`, `anthropic`,
`pysilero-vad`. The existing model extras (`faster-whisper`, `piper`)
stay their own extras.

The implementer inventories EVERY current dependency into a tier with a
reason each, in the implementation doc, rather than accepting the list
above as complete: the list is the plan's expectation and the inventory
is the finding.

**`[serve]` is an image-build and contributor mechanism, and it is
never an operator-facing concept.** The draft slipped and wrote
"Operators install `[serve]` plus their model extras", which invents a
fourth door: Python on a server host, installed by hand. #223 rules
that nobody installs the server as a Python package. Operators run the
image. Nothing in this plan, in `cli.md`, in either README or in the
changelog tells an operator to install anything with `uv` or `pip` on a
server, and the census test's exclusion review is where that is
checked, not memory.

**The three doors, each proven by something that runs:**

- **Operators** run the published image through docker compose and
  install nothing. The image BUILD installs `[serve]` plus the model
  extras the image ships, inside the Dockerfile, which is where that
  name stays; the image smoke lane is the proof, and it must run
  pre-merge via `workflow_dispatch` because the Dockerfile changes.
- **Laptop users** run `uvx --from git+...`, which installs nothing but
  the bare wheel's closure. Decision 11's lane is the proof.
- **Contributors** run `cd vinga-server && uv sync` and get a runnable
  server with no new flags, and the AGENTS.md Commands section does not
  change. The mechanism is a `dev` dependency group entry that pulls
  the `serve` extra, because `uv sync` installs the default groups and
  the project itself but not its extras. The proof is a CI step that
  syncs the way a contributor does and starts the server, which is the
  existing sync-then-run smoke pointed at a plain `uv sync`. **This is
  the one place a mistake is invisible to every other lane**, because
  every other lane names its tier explicitly.

The `[serve]` sweep is inventoried, per parked finding 13, with two
inversions from the parked shape. The AGENTS.md row is a PROOF rather
than an edit, because settled decision 3 forbids changing that section.
And both READMEs' install lines and provider-extra examples are
reviewed for the opposite of what the parked plan assumed: the parked
sweep would have rewritten
`vinga-server[faster-whisper,piper]` into
`vinga-server[serve,faster-whisper,piper]` at every site, which is the
fourth door in a code block. Where such a line addresses an OPERATOR it
is replaced by the compose invocation, not re-tiered; where it
addresses the image build or a contributor it names the extra. The rest
of the inventory: the Dockerfile, every CI `uv sync` site with its
chosen tier stated, and the `config.deploy` prose, each classified the
same way.

### 9. Six names to light homes, one module split, and the lazy arms

`config/cli.py`'s remaining reach into heavy territory, from the tree
as it stands:

- `store.check_transportable`, `store.APPLY_LOCATION` and `store.addressed`,
  which are pure functions and a constant over documents living in a
  SQLAlchemy module.
- `views.reference_value`, one pure function in a module that imports
  the store and the secrets.
- `secrets.MASK` and `secrets.provider_identity`, a string constant and
  a pure function in a cryptography-importing module.
- `onboarding.origin.onboarding_url`, whose FastAPI reach is three
  levels deep: `origin.py` imports `.keys` (line 50) and
  `onboarding/keys.py` imports FastAPI (line 48), and importing either
  first runs `onboarding/__init__.py`, which eagerly imports the whole
  aggregate package (lines 100-142). This one does not move; see below.
- `docgen.openapi()`, whose FastAPI reach is already function-local and
  stays that way.

The moves:

- **New module `config/transport.py`**: owns the recursive
  transportability policy, `check_transportable`, `APPLY_LOCATION` and
  their helpers. Two real consumers of one nontrivial policy (the store
  and the CLI), so it passes the deletion test; inlining it into either
  caller would put the policy where the other cannot read it.
- `addressed` moves beside the descriptors it reads (`entities.py`).
- `views.reference_value` INLINES into its sole CLI caller (the export
  shadow note) rather than gaining a module, because a one-caller move
  is the pass-through the design guide deletes.
- `MASK` moves beside `is_secret_option` (`models.py`);
  `provider_identity` beside the descriptors. `secrets.py` keeps
  re-exports so the many server-side callers do not churn.
- **`onboarding` does not move, and `ota-url` stays server-gated.** The
  draft proposed lifting `websocket_url_for` out of `origin.py` to make
  the URL derivation FastAPI-free. That was measured wrong: `Request`
  is not the only reach, because `origin.py` imports `.keys`, which
  imports FastAPI, and the package `__init__` eagerly imports the
  aggregate whichever submodule is named. Making `ota-url` thin
  therefore means extracting handler-free key derivation AND changing
  how the `onboarding` package initializes, which is a second
  responsibility this issue does not own: the package's shape is the
  #143 split's, and rearranging it under a CLI packaging change would
  be the length-cut the design guide refuses. So `ota-url` joins
  `openapi` in the gated set, and the idea is recorded here as
  considered and dropped rather than left to be rediscovered.

  The cost is small and worth stating: `ota-url` is a server-host
  command by nature, since it derives a URL from the file half of the
  configuration that a laptop does not have, and the laptop-side
  question it is confused with ("does that URL answer?") is
  `vinga-server doctor`'s, which #244 already made a command of its
  own. #287 revisits it, since a generated client has no onboarding
  import to inherit.
- **New module `vinga_server/serving.py`**: owns the serve lifecycle,
  `DrainingServer` (which subclasses `uvicorn.Server` at import time),
  the uvicorn configuration, startup, shutdown, the banner and every
  serve-only import. `main.py` keeps dispatch and its boundary
  sentences, imports `serving` only in the serve branch, and answers
  one fixed sentence naming the extra when a thin install is asked to
  serve. Without this split `vinga-server config ...` cannot reach that
  sentence at all, because `main.py` imports FastAPI, uvicorn,
  composition, boot, onboarding and providers before any dispatch runs
  (parked finding 3).

### 10. Structured for #287, and the structure is testable

"Structured for the exit" is worth nothing as an intention, so it lands
as three artifacts that fail when it stops being true.

- **The CLI's reach is an inventory, held by a test.** A test asserts
  the EXACT set of `vinga_server.*` modules that importing
  `config.cli` pulls in at module scope. Widening it is a review event
  with a name, and #287's "gap census of whatever grammar or help
  derivation still reads server modules directly" becomes a diff of
  that set rather than fresh archaeology.
- **The dependency arrow is asserted.** No module under `vinga_server`
  imports `config.cli` except `main.py`, inside its dispatch branch,
  and that one edge is the declared exception with a comment saying
  #287 removes it. A test enumerates importers and holds them to that
  closed set of one.
- **Answers are read only through `config/responses.py`.** That module
  imports nothing from `vinga_server` today; the test pins it, because
  it is the half a generated client substitutes for. The CLI never
  validates an answer against a server-side model.

What this plan deliberately does NOT do: move the descriptors, the
config models or the response shapes anywhere, generate anything, or
add a workspace member. All three are #287's, and doing any of them
here is the rework the ruling exists to avoid.

### 11. The wheel-grade lane, with the leak surface kept

**The thin inventory is EXPLICIT**, both ways, because a command can
fail to run thin: every command in the tree runs from the bare install
except the two gated ones, `openapi` and `ota-url` (decision 9), which
are present in the grammar and answer the fixed install-the-extra
sentence. The lane exercises both sides, and the completeness assertion
runs against the explicit inventory rather than against whatever
happened to be tested.

**Every command in the inventory is RUN, never merely imported.** That
is the distinction the gated pair exists to make: importing `cli` from
a bare wheel proves nothing about a command whose heavy import is
inside its own arm, and the draft's proof would have passed a broken
`ota-url` in either direction. So the lane invokes each thin command as
a subprocess and asserts a real answer, and invokes each gated command
and asserts the fixed sentence and exit 1. A command that moves between
the two sets fails the lane from whichever side it left.

**There are TWO lanes, and neither replaces the other.** The draft said
keeping the server in-process preserved `Watched`, which is half true
and therefore wrong. `Watched` collects log records made in THIS
process; it sees the server's records because the server runs in a
thread here, and it sees the CLI's records today because the CLI runs
here too. Move the CLI into a child and `Watched` goes blind to every
client-side record and every handled exception the client retained,
which is precisely where the refusal leaks live: #289's traceback and
#290's URL are both client-side. Capturing the child's stdout and
stderr is not the same assertion, because the existing cases read raw
log arguments, extra attributes and exception chains
(`tests/integration/test_cli_live.py`, lines 293-333).

So:

- **The in-process live lane is RETAINED as the security lane.** Every
  existing refusal and no-leak case stays where it is, running client
  and server in one process, with `Watched` reading all four surfaces.
  This is the lane that proves sentences do not leak, and this issue's
  new sentences (decision 7a) add their cases here.
- **The wheel subprocess lane is ADDED beside it for installed-artifact
  behavior**: that the bare wheel resolves, that the `vinga` binary
  exists and runs, that each thin command answers and each gated one
  refuses, that the tier closure holds. It asserts on exit codes,
  stdout and stderr, and it makes no no-leak claim it cannot support.

Child-side instrumentation that serialized log records back to the
parent was the other alternative and is rejected: it would build a
second, weaker copy of `Watched` whose fidelity nothing checks, to
re-prove in a subprocess what the in-process lane already proves
directly.

**The lane itself.** Build the wheel, `uv venv` a clean environment,
install the BARE wheel with no extras, and drive the actual `vinga`
binary as a SUBPROCESS against a live server; the server stays
in-process in the existing `serving()` thread because it is the cheap
way to have a server, not because it preserves anything.
Provenance is proven and not presumed: the lane runs from a temporary
directory outside the checkout, scrubs `PYTHONPATH` and its relatives,
and asserts the resolved package file sits inside the clean venv before
any command runs, which is the pattern the two existing wheel steps
already set. The test process still imports `cli.COMMANDS` for the
inventory map while executing through the subprocess.

**Coverage is the full registered inventory** in the wheel lane, never
a representative subset; the runtime is managed by one shared wheel
build, one venv and fixture reuse, and the measured runtime is recorded
in the implementation doc. The in-process lane keeps its own existing
completeness rule, which is #194 M3's and does not change here.

**The tier proof is a closure, not three probes.** The installed
distribution set is asserted against an explicit allowed closure
derived from the pyproject tiers, positively (every intended client
dependency present) and negatively (every serve-only distribution and
top-level module absent), so a heavy default install cannot pass by
dodging named imports.

**The client's contract is checked against the DOCUMENT.** A test reads
`docs/reference/api-openapi.json` as data, importing no `config.api`,
and holds the CLI's acts to the document's operations and component
schemas, so client and server cannot drift together unnoticed. This is
also the test #287 inherits as its regeneration oracle, which is why it
is worth more than a spot check.

Three things have to be true before that test can be written, and the
draft assumed all three. They are M3 deliverables:

- **`Act` carries its REQUEST shape as a fact.** Today it carries a
  method, a path and a renderer, and nothing says what a body looks
  like. Method, path and response alone leave the binding, secret,
  default-agent and apply bodies free to drift while the test stays
  green, and those four are exactly the bodies with adapters in front
  of them. So `Act` gains a request-shape field, `None` where the act
  sends no body, and the test compares request bodies as well.
- **The success-response shape stops hiding in a closure.** `PENDING`,
  `STATUS`, `PROMPT` and `RELOAD` all leave `answers=None` and validate
  inside their renderers (`config/cli.py` lines 2161-2182), so the
  response shape is not inspectable from the row. Listing validation
  moves out of the renderer and onto the act, which is also the
  design-guide fix: a renderer's job is rendering, and a shape that
  only its renderer knows is a fact with no home. This is the one
  production change M3 carries, and it is small; if it turns out not to
  be, it moves to M1 with the rest of the table work and the
  implementation doc records the move.
- **The covered operation set is CLOSED, with a stated exclusion set.**
  The document carries operations no config-CLI act covers: the
  conversation and session routes, the collection reads the admin UI
  uses, `/healthz`. An unqualified both-ways comparison over all
  operations cannot pass, so the test names the covered set and an
  explicit exclusion set with a reason per entry, and asserts their
  union is the whole document. That is what makes a NEW route fail the
  test rather than slip past it: an operation in neither set is the
  failure.

### 12. Version and skew, pre-1.0

No negotiation machinery. The committed OpenAPI document is the
contract and its `API_VERSION` is the handle. `vinga --version` prints
the installed distribution's version (M1, decision 7). The policy,
documented in `cli.md` (M3): pre-1.0, run the CLI from the same release

skew incident or 1.0, recorded as the deliberate floor.

## Risks

- **A missed heavy import at module scope** turns the thin install into
  an ImportError at first use. The clean-venv closure is the guard, and
  it imports the CLI module itself rather than only the package.
- **The recipe prefix trap** (decision 6). If the example files and the
  renderer disagree about the program word, the recipes region renders
  empty and CI fails on an unrelated change. Mitigation: one canonical
  constant, the examples respelled to it in the same commit, and the
  recipes drift step read in the M1 diff rather than trusted.
- **The differential fixtures are captured from the pre-rename commit**,
  which means they have to be generated before the reshape and carried
  through it. If they are regenerated after the change they prove
  nothing. Mitigation: the fixtures land in their own commit, first,
  with the generating command recorded beside them.
- **The lock and CI churn.** Re-tiering rewrites `uv.lock`; every CI job
  that syncs must name its extra or deliberately not, and the
  implementer lists each site with its choice.
- **The wheel steps' semantics shift.** The existing migrate-from-wheel
  and render-from-wheel steps assume the wheel serves; they now install
  `[serve]` explicitly, and the NEW lane is the one that installs bare.
  Both are asserted so neither quietly tests the other's configuration.
- **The contributor door fails silently** (decision 8). Every other lane
  names its tier, so nothing else would notice a `uv sync` that stopped
  producing a runnable server. The sync-then-run smoke is the only
  guard, and it is named as such.
- **`events.md` moving is deliberate exactly once.** The drift
  assertions treat it as forbidden in M2 and M3, so a stray reword
  after M1 fails.
- **Every sentence this issue adds is a new no-leak surface**, and the
  temptation on each of them is to say which entry is meant. Mitigation:
  decision 7a, fixed constants with exhaustive per-field sentinels.
