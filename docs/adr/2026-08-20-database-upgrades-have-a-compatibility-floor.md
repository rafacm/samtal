# Database upgrades have a compatibility floor

**Status:** Accepted (recorded 2026-08-20, as milestone M7 of the
#210 governance simplification plan)

## Context

The repository is labeled early development, but it publishes a
deployable image on every push to `main` and documents persistent
database volumes, backup, restore, and encryption key handling. The
repository cannot prove whether third parties run deployments, but
its deployment model permits them, so pre-release does not
automatically mean disposable data. The #210 architecture review
asked whether the migration history (four configuration revisions,
one conversations baseline) was governance worth its cost, and
concluded the cost of keeping it is three small files while the cost
of rewriting it is real: a database stamped at a rewritten baseline
would be considered migrated while lacking folded-in columns, later
revisions would refer to removed ones, there is no complete YAML
importer to rebuild configuration and encrypted secrets from, and
the existing upgrade tests deliberately prove that data survives
migration from the first revision.

**Addendum, 2026-08-22 (issue #225).** The audit the last consequence
below sent to its own issue settled the stance this Context left open,
and the settlement belongs here rather than only in that issue. The
project is pre-release, says so in a notice nobody reading it can miss,
and has declared no beta. No third-party installation is known: a
deployment model that permits one is not evidence that one exists, and
the maintainer's own boards are resettable, their configuration a file
and a database that can be rebuilt from it. So tolerance for a state
only a pre-release build could have produced is cost with no
beneficiary, and a refusal path may stop accepting a shape no supported
deployment produces. That is what licenses the deletions recorded under
issue #225, and it is bounded twice: it does not reach the databases,
whose floor the Decision below sets and which this addendum leaves
exactly as it is, and it ends the day a beta is declared.

## Decision

- **Upgrades are supported from the first beta image onward.** The
  day a build is called a beta, every database that image creates or
  touches is upgradeable by every later image, and that promise is
  what "beta" means here.
- **Until a beta is declared, upgrades are supported best-effort
  from revision `0001` forward.** A deployment tracking `latest`
  gets reviewed migrations for every schema change, which the
  existing upgrade tests already prove from the baseline; what it
  does not get is a promise that no future decision will ever
  require a reset, only that such a decision would be recorded, not
  slipped.
- **Migration history is never rewritten as a cleanup.** Squashing
  or pruning revisions is a compatibility decision: it requires a
  new record superseding this one, an explicit statement of which
  databases become unsupported, and a tested reset or
  export-and-reimport path. Saving migration files is never by
  itself a reason.
- **Every schema change continues to arrive as a reviewed
  migration**, with generated revisions treated as candidates for
  review, not as truth.

## Consequences

- The four configuration revisions and the conversations baseline
  stay as they are; nothing is squashed.
- The wheel-migration CI step keeps proving that a fresh database
  built from the shipped artifact reaches the head of both chains,
  and the upgrade tests keep proving data survives from `0001`.
- Declaring a beta acquires a new obligation and therefore a
  checklist item: from that image forward, a migration that cannot
  upgrade in place is a bug, not a decision.
- The wider question the review raised, which other compatibility
  branches in the code are load-bearing corruption recovery and
  which are obsolete pre-release history (old MCP grant forms,
  previously accepted provider URL shapes, recovery for legacy
  names), is a separate audit tracked in its own issue; this record
  covers the databases only.

## Addendum, 2026-08-23 (issue #243): the domain chain is squashed

The third Decision bullet above says that squashing migration
history is a compatibility decision requiring a new record, an
explicit statement of which databases become unsupported, and a
tested reset path. This is that record, and it exercises that
clause rather than overriding it. The Decision itself is unchanged:
the first beta image still starts an upgrade promise, and every
schema change still arrives as a reviewed migration.

**The decision.** The domain configuration is now stored as one
validated JSON body per entity beside its key and secret columns
(#243), which no in-place migration can produce without rewriting
every row through the models it is meant to be independent of. The
domain chain `0001` to `0004` is deleted and replaced by a single
autogenerated, reviewed baseline under a revision id nothing was
ever stamped with, `2001_json_body_baseline`. The conversations
chain is untouched: it is a single baseline already, it is a
separate file with its own version table, and nothing here reaches
it.

**Which databases become unsupported.** Every domain database
written by an image carrying the `0001` to `0004` chain, that is,
every domain database in existence before this change. There is no
upgrade from one and there will not be one. Such a database is not
mistaken for current: the new revision id is fresh, so Alembic
cannot locate the stored revision and `db.migration_failure`
answers with a sentence saying the database predates the storage
reshape, to reset the directory and re-seed, and naming this record.
That sentence is the whole of the operator-facing surface of
"unsupported".

**Two Consequences bullets above are retracted by name.** The first
("The four configuration revisions and the conversations baseline
stay as they are; nothing is squashed") is false of the
configuration revisions from this change on, and remains true of the
conversations baseline. The second's second half ("the upgrade tests
keep proving data survives from `0001`") is retracted whole: those
tests and their fixtures are deleted with the chain they were about.
The second's first half stands and is strengthened: the
wheel-migration CI step still proves that a fresh database built
from the shipped artifact reaches the head of both chains, and now
also that the domain head is exactly one revision and that every
entity table has its body column.

**This crosses the bound the #225 addendum drew for itself.** That
addendum licensed dropping tolerance for shapes only a pre-release
build could have produced, and bounded itself twice: it did not
reach the databases, and it ends when a beta is declared. Its
reasoning is what applies here, extended past the first of those
bounds deliberately and by a record of its own: the project is
pre-release, no third-party installation is known, and the
maintainer's own deployment is a volume that can be reset and a
configuration that can be rebuilt. The second bound is untouched,
and is in fact what this makes concrete: the forward-only promise
below is the one a beta will convert into an upgrade promise.

**What "tested" means, inside this repository.** The Context above
objected that there is no complete YAML importer to rebuild a
configuration and its encrypted secrets from, and that objection is
answered rather than waved past. Two suites exercise the reset path
end to end on a fresh database, and both run in CI:

- the example-fragment install suite
  (`tests/integration/test_config_examples.py`), which installs every
  committed example fragment into an empty database and boots a
  server on the result, so "rebuild the configuration from files"
  is a thing this repository does on every run rather than a plan;
- `set-secret` re-encryption, which is how the credentials come
  back: a secret is read from the environment and encrypted under
  the configured key into the entity's own secrets column, so
  re-seeding a volume restores the secrets from the environment the
  deployment already holds rather than from a backup of ciphertext.

The operational half is the infra re-seed job, which runs the same
two steps against a real deployment on the day the image lands. The
deploy sequence matters and is recorded with the implementation: the
volume is reset **together with** the image bump, never after it, so
no build ever meets a database it cannot read.

**The compatibility surface moves to the models, and it is pinned.**
With no columns and no per-entity mappers, what a stored row means
is what its pydantic model says, so the promise this record now
carries forward is that every new model version parses every stored
body. That is pinned by committed bodies under
`vinga-server/tests/unit/data/domain-bodies/`, one sparse and one
fully written per kind and both MCP transports, which the body-parse
family validates through today's models on every run. A model change
that cannot read one fails CI until either the model tolerates it or
the fixture is deliberately updated with a compatibility decision
recorded beside the change. That is the floor a beta will stand on,
and it holds from here to that day.
